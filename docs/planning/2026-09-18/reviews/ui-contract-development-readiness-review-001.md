# Xanthil Desktop UI Contract Development-Readiness Review 001

## Review control

| Field | Value |
|---|---|
| Reviewed input | JuanerAI Product Development Blueprint v1.0 and Xanthil Desktop UI Contract v1.0 before correction |
| Reviewer | Fresh read-only support Agent with implementation-worker perspective |
| Review scope | Readiness to create the high-fidelity clickable UI Contract only |
| Date | 2026-09-18 |
| Verdict | `NEEDS_CLARIFICATION` |

## 1. What I Would Build

A high-fidelity, explicitly simulated Xanthil Desktop Free prototype for a
non-technical membership-operations analyst. It would demonstrate the six-step
Decision Case from Case creation and two-file import through evidence review,
candidate comparison or insufficient-evidence closure, preservation and export.
It would visibly enforce macOS, UTF-8 CSV, CNY, Asia/Shanghai, local-first,
optional model exposure, no Action and no Outcome boundaries.

The prototype would use labeled synthetic data and simulated execution, cover
the happy path and thirteen visible failure classes, and demonstrate keyboard,
focus, status, error and recovery behavior at both required viewport sizes. It
would not claim computation, persistence, provider invocation or integration.

## 2. Required Guessing

The supplied package would require the prototype builder to invent:

- the exact Finding-acceptance and Decision-closure interaction that moves a
  Case from Review to Completed;
- the allowed recovery action, preserved state and target state for each of the
  thirteen failure classes;
- which user actions invoke optional model assistance, which payload is shown,
  and where refusal or provider failure returns to the manual path;
- the editable boundary and default support, refutation and sufficiency rules
  for H1, including equality and zero-denominator behavior;
- who creates DecisionCandidates and which validation permits closure;
- the local-data authorization confirmation and the reviewable-versus-blocking
  import taxonomy.

## 3. External Study Required

No external study was used or needed to identify the gaps. If PX-2026-004/006
are intended to impose visual or interaction constraints beyond the principles
written into the plan, those constraints must be attached or summarized. The
unlisted Demo repository cannot silently supply missing product requirements.

## 4. Untestable Requirements

- “Every required visible failure class” lacked an expected state, preserved
  history, permitted recovery and resulting state.
- “Business-language comprehension” lacked a task and observable pass
  condition.
- Model-refusal and provider-failure continuation could not be demonstrated
  without a defined assisted action and manual destination.

## 5. Correctly Deferred

Exact component libraries, pixels, implementation details, schemas,
migrations, storage layout and resource limits were correctly deferred. Actual
provider/model selection, a second Runtime, enterprise controls, Action,
Outcome, extra platforms and formats, and Model Pack activation were also
correctly outside this slice.

## 6. Required Plan Additions

1. Add a self-contained Case/Run transition table.
2. Add a thirteen-row failure and recovery matrix.
3. Add an optional model-interaction table with full manual alternatives.
4. Freeze H1 edit, support, refutation and insufficiency rules.
5. Define manual DecisionCandidate creation and the exact completion action.
6. Define data-authorization confirmation and import-issue taxonomy.
7. Replace subjective comprehension language with observable UI Gate tasks.

## 7. Verdict: NEEDS_CLARIFICATION

The package fixed the audience, first-slice boundary, information architecture,
method display, non-goals and stop line, but still required load-bearing guesses
about state, recovery, model interaction, hypothesis, candidates, data authority
and acceptance. It was not yet sufficient frozen input for the clickable UI
Contract.

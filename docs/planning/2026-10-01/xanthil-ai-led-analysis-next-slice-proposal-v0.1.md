# 阶段建设与下一纵切建议 v0.1：AI 主导的会员复购分析交付

2026-10-01 · `PROPOSED_FOR_USER_CONFIRMATION` · 配套 [Blueprint v4.0 草案](juanerai-product-development-blueprint-v4.0.md)。

这是有限阶段产品及其能力组合、首条验证纵切的选择建议，不是已冻结产品输入、OpenSpec Change 或 UI Contract。用户确认后，由另一 session 组织正式范围、Change 和新 UI Contract；本 session 不生产实现。

## 1. 推荐结果与取舍

**用户说出问题、提供获准资料；AI 组织并持续推进分析，先交付经验证的发现，再交付可点评报告与待审建议；用户只在业务缺口、重要授权和判断点参与，最终记录自己的选择。**

沿用现有会员复购场景，不更换 Runtime，不重建已完成计算／验证／历史能力。先证明这一项任务比现有流程更容易完成，且比通用 Agent＋Skill 有值得付出的独特价值，再推广交互与后台机制。

推荐组织方式：**有限阶段完整设计 → 按依赖成组建设能力 → 纵切持续验证 → 同一集成版本的阶段整体验收。** 产品目标完整，工程提交保持小；不要求每项共享核心工作都伪装为一个小用户故事，也不等所有能力完成才第一次集成。

不是：减少几个按钮；在聊天中逐一复刻表单；AI 展示计划后仍等用户逐节点点继续；一次投入全量后台／语义／假设／策略平台；先做更多协作工具再等待核心任务体验改善。

## 3. 最小场景与业务边界

阶段名称建议：**P1 个人会员分析完整任务体验**。这是有限阶段，不是整个 JuanerAI，也不是预定单个 Change。整期产品终点是自然开始、系统推进、经验证的可点评结果与人的下一步选择。

目标用户：非技术会员运营负责人。示例需求：“最近会员复购似乎下降，帮我核实变化，说明目前能判断什么，并建议下一步。”措辞不是固定 Prompt，也不预设一定下降。

资料仍为获准 UTF-8 `members.csv` 与 `orders.csv`；沿用 CNY、Asia/Shanghai、两期复购定义、原有效订单／数据质量规则、M1 比较和适用的 M2 分组贡献。列名识别和已配置映射用于减少劳动，不能改变分母、有效状态或口径。

只有预先配置的口径、用户明示的事实或可靠来源可以确定业务意义。未知期间、对象、状态含义、映射歧义或重大数据质量处置才需询问；能从获准资料得出的技术事实由系统处理。首次场景配置不完整时，向用户解释具体缺口或转维护职责，不要求普通用户填齐整套分析流程。

结果允许：支持下降、不支持下降、证据不足；有依据的继续调查、补资料、暂缓、不行动或候选比较。不得从两期变化声称原因已确定、策略有效或行动已执行。现有极小夹具两期 50%→50% 仅用于反驳错误前提，不代表真实业务效果。

本期完整任务族至少包含：核实两期总体变化；在已支持分组资料和条件下检查分组贡献；点评表达及改变受支持的两期时间范围后得到新的受控结果。它们消费同一套语义／方法／IR／执行能力，不为每条故事复制一套独立管线。新增人群筛选算子不由此授权；具体合法组合由正式范围确认，不扩成任意因果问题或通用分析。

前期澄清／能力不足的交互属于本期，但真实联网研究、多源数据库、自由文件检索、因果／预测建模、完整 OSM、团队协作、业务自动行动及资产自动发布不在本期。用户问到这些时，应说明当前可回答部分及缺什么，不诱导虚假完整答案。

## 4. 改进后的完整任务路径

| 环节 | 用户做什么 | 系统持续做什么／当场价值 | 何时才停下来问 |
| --- | --- | --- | --- |
| 开始 | 用自然业务语言提出问题；必要时选保存位置／提供文件 | 复用允许的上下文，识别是否属于当前支持场景，给出可回答范围 | 意图影响分析方向，或任务超出能力／数据权限 |
| 补齐 | 提供缺失材料，回答真正业务缺口 | 识别资料角色、可用字段和覆盖；复用配置；说明缺口的影响及最少补法 | 关键语义不能可靠确定；提供“补充／缩范围／先保留未知”等实际选项 |
| 授权并推进 | 理解并授权本次目的、来源、模型可见内容、操作和资源上限 | 在授权内连续预检、形成快照、计算、独立验证；进度按业务意义呈现 | 需要新来源、外发范围、资源／工具权限或重要口径变化；不是每个内部步骤 |
| 首个发现 | 读结果，可质疑或更改问题 | 尽早说明“发生了什么、依据、不能判断什么、下一步”；不中断必要验证，不把猜测包装成发现 | 验证失败、证据不足或需要新的业务判断；不得编造结果来保持流畅 |
| 报告与比较 | 点评、要求修改或深入一项争议 | 自动形成待审报告与有依据的候选；解析点评，区分表述修订与需要重算的变化 | 改变口径／资料／权限或模型调用超范围；纯同范围工作继续推进 |
| 作出判断 | 接受／质疑有限结论，选择候选／不行动／暂缓／补证，确认适用预期与责任 | 用业务可读摘要展示要正式记录的内容，保存后给出可理解回执及后续状态 | 明确的人工决定；不能从“继续”“收到”“写得不错”推定正式选择 |
| 返回／改想法 | 重开、暂停或修改需求 | 保留有效工作，说明变更影响、仍有效结果和需要重新工作的部分；旧链可查 | 需要新的授权或判断，而非要求用户重新操作全部内部节点 |

产品可以展示聊天、卡片、表格和报告组合，不强制聊天作为唯一交互。主区域是用户正在解决的业务问题与结果，过程／证据／口径／高级控制按需展开；关键不确定性和授权影响不能隐藏到专家页。

## 5. 推荐的产品决定与现行合同差异

以下均为**待用户确认方向、待技术可行性及新 UI 合同关闭的变化**；批准建议不直接替换 canonical specs。

### D1：允许 AI 从未完成任务开始，而非等 Completed

复用已有问题整理、模型配置、Pi Adapter 和分析 Application。新增任务入口可整理需求并推进已获准分析，不能把现有 Case Assistant 的 Completed 前置简单去掉后假称语义相同。

### D2：从逐项调用确认改为有界的任务授权

将 Provider／模型等维护性设置留在设置面；设置完成不等于调用获批。任务前台说明“为哪个目标、用哪些资料、向哪个模型发送什么、可做什么、预算／有效期／停止条件”。

原始 CSV 行和 `010_draw` 仍留本地；模型仅能使用本片明确准入的问题文本、必要业务语义、经过边界处理的结构信息及批准类别的聚合／验证／报告材料。后续生成的材料也必须满足可执行的出站约束，而非笼统批准“未来所有内容”。精确字段、敏感结构信息处理、预算和可行的任务有效期在正式输入冻结前关闭；不在蓝图层发明 API／Schema。

推荐授权内的同目的连续调用／修订不逐次弹出技术审批；新目的、来源／接收方、材料类别、工具、额度或业务外部影响重问。查看调用历史与精确载荷的能力保留，数据权不由模型猜测。技术架构须评估这项对现有“精确 Attempt 载荷＋只读工具”合同的影响。

### D3：系统生成待审结果，不伪造人工接受

主算／复算一致后发布明确标为系统验证的 Finding；可继续生成待审报告和候选建议，不等用户先点接受才能做有用准备。仍不得写入人工 Finding acceptance 或正式决定。

用户最终业务审阅须看懂要接受的有限发现、要记录的选择、责任和适用预期。一次明确操作可以承载已经清楚展示的多个效果；无须人为保留“一对象一确认”，但不能含糊合并。拒绝某个发现或暂缓时不得暗中接受它；应停在待补证／未形成正式决定的诚实状态，或进入现行允许的相应决定路线。具体合法组合由后续产品输入及 UI 明确。

### D4：Closure 和首次正式草案不再是用户手动组织的两次“完成”

待审材料可以先准备，用户在连续任务中作出最后判断；系统处理适用的内部记录顺序与一致性。沿用 Decision／Expected、历史追加和过期阻断，人的选择不是行动授权。

这是现行发布前置及状态关系的合同变化，不是隐藏按钮。内部事务／失败恢复由工程设计，但前台在成功、部分失败、重试或来源过期时承诺什么，必须在产品／UI 合同中说清。首次纯人工正式草案不是本片主目标；如需新增离线旁路，须明确人工来源与范围，不伪造模型 Attempt。

### D5：报告点评必须真的驱动工作

“简短一点”属于表达修改，不能改变数字／来源；“改用另外两个期间”须形成适用的新口径和授权，旧结果不可作为新问题答案；“只看上月新客”若需要本期未支持的人群筛选，须说明能力不足而非偷偷扩范围；“为什么下降”如现有方法不能回答因果，说明限制并建议可验证的补证，而非编原因。既有判断不得被模型修订静默覆盖。

### D6：Fork／Subagent／Skill 不是前置学习要求

保留 003 功能和专业控制，在适用资格满足时以“比较另一思路／检查反证”等任务入口出现。先用已有单任务能力达到连续交付，不把自主派发、递归、并行、材料授权自动继承纳入本片。系统可提出有用检查建议，不擅自发起权限未闭合的子任务；Skill／已配置方法优先作为后台能力复用。

## 6. 失败、缺证、停止与改变想法

| 情形 | 产品必须做到 | 不可用的简化 |
| --- | --- | --- |
| 资料不足／语义不明 | 指出哪项结论受影响、已知什么、最少补什么或如何缩问题；保存已知内容 | 重复整套问卷；静默造默认业务事实 |
| 计算／复算不一致 | 不发布该结论；说明失败及可行修复方向，保留诊断和有效前置资料 | 让 LLM 投票选择数字；用上次成功结果冒充本次 |
| 模型失败／额度耗尽 | 保留确定性发现和草稿，区分哪些还没完成，允许用户选择恢复或停止 | 为“自动化”无限重试、偷偷换 Provider、扩额度或把失败记完成 |
| 用户停止／关闭 | 停止后不继续发起新工作；如有无法撤销的在途调用，明确显示实际状态与费用／结果边界 | 默默后台续跑；收到迟到结果就自动正式采纳 |
| 修改资料／目标／口径 | 说明影响、保留历史、隔离过期材料，按权限重新推进必要部分 | 静默沿用旧批准、旧 Finding 或旧决定 |
| 记录／发布部分失败 | 明确哪些已保存、哪些未生效，避免重复记录；可检查／恢复 | 把一串内部命令默认当作已实现原子事务 |

任务内技术重试是否能自动及其资源约束、用户停止后的恢复条件等由正式输入明确，再由架构／工程实现；推荐不要求用户调度普通可恢复步骤，但不能继承原任务停机授权或默许外部调用。

## 8. 新 UI Contract 应验证什么（下一 session 制作）

沿用已有 Xanthil 工作台及能力库存，设计新任务主路径。必须直观看到：无需先选专业模式／理解内部对象即可提出问题；已知条件不重复问；系统实际推进而不是表演进度；有用结果与限制；报告点评产生区别；明确的人类判断；证据和高级控制可展开；失败、暂停、重开、改问题后仍知道怎么继续。

## 9. 三类验收：同一阶段产品上的场景、能力与体验

### 9.1 基线计划

正式输入冻结前，以同一支持场景、预定数据规模和问题脚本，观察当前 Change003 产品从空白到首次有用发现／最终判断的过程。区分首次后台配置成本、首次业务任务、复用配置后的重复任务；不能把成本从前台转给隐藏人工而宣称节省。

记录未帮助／帮助后完成、用户停顿原因、业务输入／判断与机械流程操作、首次资料缺口反馈、首次经验证业务发现时间、形成可行动结果时间、模型／计算等待、成本及结果理解。未知仍写 UNKNOWN。

同时准备同数据、可比模型／预算／权限的 Agent＋Skill 对照。无公平可行对照时标“未比较”，不宣称产品优于 Skill。此次规划不授权运行真实模型、业务数据或成本试验；后续须取得对应权限。

### 9.2 推荐验收方向

下列是产品结果标准。具体观察人数、数据组、时间／负担改进阈值及成本预算须在正式输入冻结前提出并由用户确认，**不能在看完结果后调整**；当前草案不编造 30 秒或某个提升比例。

| 维度 | 必须证明的结果 | 失败例子 |
| --- | --- | --- |
| 独立开始与完成 | 首次非技术用户无口头代操作即可从业务需要开始，在支持范围到达正确发现及本人选择；不先学 Case／IR／Fork | 演示者指导每一步；只证明熟练开发者能点通 |
| 首次有用结果时间 | 分别衡量资料可行性反馈与经验证业务发现，后者有来源、限制与下一步意义；相同任务对照 | 把欢迎语、计划或报错当作业务发现；预置结果 |
| 人工负担 | 常规成功路径无需逐节点启动／批准内部处理；重复任务复用配置，只追问新增业务缺口 | 以聊天问卷替换表单，仍由用户安排每一步；将后台人工劳动漏计 |
| 结果理解与行动 | 用户能说明主要发现、依据、关键限制以及自己为何选补证／暂缓／不行动／候选；能区分建议与实际行动 | 能复述报告但不知道能做什么；将相关性／模型意见误认为因果证据 |
| 点评与改意图 | 表达修改保留事实，范围变化确实改变受控执行／结果，旧记录不改写 | 只换措辞；旧数字重新包装成新分析 |
| 失败后继续 | 用户知道失败在哪、什么仍有效、最少下一动作；适用恢复不要求重做全部准备 | 无限重试／重新填全部表；用户无法判断是否还在收费或执行 |
| 安全与权威 | 原始数据不越界，预算／工具受约束；未决定不产生正式选择，停止／过期／来源错配可验证拒绝 | 用减少确认掩盖扩权；用户说“好”被隐式当作正式采纳 |
| 相对价值 | 与当前产品及 Agent＋Skill 比较质量、时间、用户劳动、维护成本和可检查／重复利用收益 | 只证明按钮更少、输出更长或机制更多 |

实际质量验证至少覆盖：前提成立／不成立、关键缺数／语义歧义、不同问题表述、点评、范围改变及失败恢复。固定模型替身可证明机制，不能证明实际 AI 理解／建议质量；真实模型测试同样不能替代非技术用户观察。UI 接受、工程接受、体验结果分别记录，不追加一套治理平台。

场景验收在同一固定集成版本从空白任务开始，而不是分别用预建的 Completed Case 展示每个模块。正常总体／分组任务及关键反例、失败、修改、重开均走适用真实入口；数据规模与具体案例在正式输入中钉住。

能力验收除各模块自己的正反测试外，必须有下列真实消费证据：

| 完整能力链 | 本期通过条件 | 明确不够的证明 |
| --- | --- | --- |
| 语义上下文→计划 | 同一受版本约束的场景配置被多个合法任务变体实际消费；歧义／不兼容版本阻断，不能静默猜测或改用 latest | 只记录配置文件、在测试中手填同名字段 |
| IR→执行→验证 | 合法计划变化实际改变方法选择／参数及适用执行结果；不支持／错配拒绝；计算和独立验证绑定同一输入与计划 | 保存五步 IR、对照 hash 后仍无视计划执行固定另一条路 |
| Evidence→报告→点评 | 报告数字／依据来自本次证据；表达修改不改事实，范围修改形成适用新执行／报告；旧证据不能冒充新结果 | 固定模板填预置答案；只编辑报告文本 |
| 任务授权→工具→结果 | G2 的实际调用只在本次授权的工具／内容／预算内，跨范围必须停；非成功路径无未授权继续或正式采纳 | 模型口头说遵守；只检查 UI 禁用按钮 |
| 用户决定→历史 | 正式选择及适用预期来自清楚的人类意图，记录正确版本；未决定、拒绝或失败不生成虚假决定 | 以聊天肯定语、计算通过或模型推荐代替采纳 |

工程可分多次提交与局部验证，但阶段接受时须同时提供场景、能力和体验结论及未验证项；三者不能互相替代。具体测试机制、事务设计和回退办法交工程，而不是在本建议中冻结实现。

2. 接续 session 完成阶段产品设计、新 UI Contract 与受影响合同语义，用户确认 UI；在正式输入冻结前关闭数据／工具授权、失败恢复和体验测量条件。无需预设计远期平台。
3. 开发流程职责依据批准结果及技术依赖组织 Change：尽早取得 G1 的真实有限消费链与 G2 最小可用调用接缝；接口清楚后允许独立工作并行，不先做大批不可集成模块。
4. 成组补齐 G1／G2／G3，同时持续用首条任务纵切验证；工程内部小提交、对应测试、可回退。每个 Change 交付其能力增量、当前消费者及剩余缺口，不向用户宣称阶段已经完整。
5. 固定整合版本，展示完整任务族、能力全景和三类验收。缺口影响本期结果就继续修复或由用户明确减范围，不以已通过故事数结束阶段；通过后返回结果回访，再推进下一 Case 采用。

这不是要求先完成所有底层再做前台，也不是预定三大 Change。Change 的数量、职责路径、测试命令与实现次序由接续规划／工程在确认范围内决定；重要依赖／合同先关闭，普通实现细节不再形成跨 Controller 审批链。

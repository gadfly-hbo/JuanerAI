## 1. 定位、变更理由与采用规则

JuanerAI 仍是从专业个人走向团队和企业的 Bottom-up Decision Intelligence System。Xanthil 是统一工作台，以可信分析进入 Data → Decision → Action → Outcome，再以受治理的改进影响下一次判断。分析可止于有边界的洞察，不强迫行动；记录和治理的成本必须由用户获得的价值证明值得。

### 1.1 延续 v4.0 的人机与前后台调整

v3.0 保留了完整能力与可信边界，但实际产品把不少任务推进责任留给用户。用户明确反馈“严谨，但很难用”，并指出流程配置、指标体系、假设库、策略库应属后台，而非普通用户开展每次分析的工作。

v4.0 改变了人机责任、前后台职责、阶段目标、建设组织及体验验收终点；v4.1 保留这些已批准方向，不将本次小版本视为重新规划：

| 维度 | v4.0 起已批准的调整 | 保留的约束 |
| --- | --- | --- |
| 用户角色 | 从流程操作者转为需求提出者、业务判断者和决策责任人 | 必要的信息、数据权限和重大业务选择仍由人提供／决定 |
| 系统角色 | 在已批准范围内理解目标、组织工作、调用能力、检查结果、调整下一步并交付 | 不推定未知事实，不替人接受结论或批准业务行动 |
| 前后台 | 前台围绕任务与结果；复用配置、专业资产和执行机制在后台 | 有业务影响的口径、限制、授权和证据仍可理解、可检查 |
| 近期路线 | 001～003 之后先补“AI 主导的一项完整分析任务”，再返回结果回访与下一 Case 采用 | 不撤销任何已完成成果，不取消完整六＋二能力目标 |
| 建设方式 | 有限阶段完整设计、共享能力成组建设、纵切持续验证、阶段性整体验收；不要求所有工作都是小用户故事 | 工程仍小步提交、测试与可回退，不等全部横向模块完成才首次集成 |
| 验收 | 分别验证场景、能力、体验，并在同一阶段产品上共同成立 | 工程 PASS、用户 UI 接受、真实使用价值分别报告；故事数量和代码量不是进度代理 |

白皮书仍是蓝图的核心参考与商业化纲领；获批、经独立就绪审查并整合进项目规则的蓝图才是产品开发最高执行指引。白皮书变更仍须用户通知、来源核对、采用决定、蓝图修订、独立就绪审查及规则整合，不能自动改写在研 Change。

### 1.2 已有白皮书采用范围不缩水

延续 v3.0 §1.2 的全部采用判断：Bottom-up DI、Decision Lifecycle、Case／Loop／Graph、System of Record、Personal／Team／Enterprise、Decision／Expected／Actual／Evaluation、受治理学习、五类 Core、IR／语义、Domain／Model Packs、OSM／PIM、三模式、DAME、Report Studio／Deep Research 及专业竞争评估。

Graph 是有权限和来源的关系能力，不预定图数据库；Hypothesis／Strategy 双库有独立权威与版本，不是聊天记忆。企业 SSO、多租户、跨客户学习、大规模 Serving 和真实业务自动行动仍按需求与专项授权推进，不成为个人任务自动化的前置条件。旧“Desktop 完成后才能开始 Model Pack”的顺序仍作废。

### 1.3 v4.1 的有限增量

1. 体验与 Analysis Core 同阶段建设，最低数据／语义／执行基础随 P1 接通；不是先做前端，再做后台。
2. P1 之后按真实任务或回访阻塞扩展数据与语义；已有来源足以支持合格 Actual 时直接推进反馈，不等待完整语义平台。
3. 在 P1 场景、能力、体验共同通过后，可讨论有界单场景商业试用；不以全模块、OSM、Team 或 Enterprise 齐备为前置，也不自动获得试用权限。
4. 采用静态技术评审识别的真实消费、任务累计授权、整体人审和兼容约束；保留 P1 方案细化、UI Gate、工程合同与实际验证的独立责任。
5. 沿用唯一累计覆盖清单及 40 个稳定 ID，把路线缺口用于排序；既有能力／验收状态不因蓝图换版升级。

这次调整不撤销、代改或重启正在准备的 Change／UI，不新增第三个平台 Change，也不改变工程唯一执行政策。

## 2. 人机分工、前后台与产品语义

### 2.1 前台只要求用户完成有业务意义的工作

| 用户活动 | 产品应承担的工作 | 必须留给用户的判断 |
| --- | --- | --- |
| 说出分析需求 | 理解目标、利用已获准上下文、识别范围及重要缺口，建议可回答的问题 | 澄清真实意图、关键约束和无法从现有资料确定的业务事实 |
| 提供缺失资料 | 识别已连接且有权限的材料；说明缺什么、为何缺、如何补；检查人工上传资料 | 选择获准来源、补充非系统所有的资料；不默认扫描本地目录 |
| 判断发现 | 自动准备、计算、验证；区分事实、模型解释、假设和未知，尽早交付有用发现 | 质疑、接受有限结论、改变问题或要求补证；不需手动批准内部计算节点 |
| 点评报告 | 形成可读报告，解释限制；将点评转成受控修订并说明影响 | 内容取舍、业务表述及修改意图；不能通过“润色”改写事实 |
| 选择决策建议 | 整理可选行动、依据、风险、条件和适用预期，包括暂缓／不行动 | 最终选择及责任、适用预期；建议、选择与行动授权不同 |
| 反馈执行与结果 | 在有授权和来源时取得资料、对照事前预期、提示缺口并准备评价 | 补充系统未掌握的事实、判断结果与后续方向；不为系统造齐“闭环” |

“人工只做决策”在这里指**不让人主导内部流程推进**，不排除必要的需求交流、资料提供、审阅和授权。系统不能用减少操作为由替用户承担责任，也不能将每个内部状态转换都包装为必须由人回答的问题。

### 2.2 后台是可复用的专业能力与维护职责

后台维护：分析流程／方法配置、指标和口径、数据源与语义映射、假设库、策略库、Domain／Model Packs、Provider 与预算政策、权限和验证规则。首次配置后在适用范围复用；配置变更由有职责的人或获准机制维护，不要求普通用户每次重建。

“后台”是产品职责划分，不预先决定新增后台网站、服务、数据库或平台。近期可先由产品交付一个经过验证的场景配置与最小维护入口；只有真实维护需求出现，才建设对应管理能力。普通分析者不必先成为指标管理员、流程设计师或 Prompt 工程师。

后台方法不等于固定脚本流水线。AI 可以在当前授权和已支持能力内，根据证据选择、组合和调整步骤；不会的能力如实告知。已有事实与明确配置不重复追问；影响结论的缺口必须问，不能把列名相似或模型高置信度当作业务语义确认。

### 2.3 AI 推进任务，确定性机制守住权威

- AI 负责理解、计划建议、解释、对话和已获准能力的调度；Application 负责实际任务推进及状态一致性，领域规则与执行器负责约束、计算和验证。不是所有处理都要调用 LLM。
- 系统自动完成可验证、可撤销、在既有授权内的内部工作。用户可以随时查看过程、暂停或改变目标；系统说明已完成、仍在做、为何等待，以及哪些结果仍有效。
- 任务内自动生成发现、待审报告和候选建议，不等于人工接受 Finding、正式采纳 Decision 或批准业务行动。系统不得伪造这些人的记录。
- 授权应以用户可理解的任务边界表达：目的、来源、模型可见材料及接收方、允许操作、资源限制、停止点。批准边界内的重复内部动作不逐项向用户索取“继续”；边界外的新数据、外发、成本或外部影响必须重新决定。
- 上述任务级授权是**拟议合同变化**，不宣布现有逐次披露合同失效。精确技术约束、可执行性和负面验证由技术架构评估与后续工程设计落实，无法可靠约束时不开放对应自动化。
- 外部业务行动始终单独授权，不能由分析任务授权推导；需要其自身权限、幂等、审计、接管与恢复合同。

### 2.4 核心语义不合并

Case 从问题开始，不是聊天标题或单次 Run。分析完成、人的决定、行动完成、实际结果评价分别表达。Expected 在观察前记录；Actual 有独立来源，不能由模型猜测或由 Expected 复制。Evaluation 区分执行符合性、观察变化、预期校准、策略归因和当时决策质量。

Finding 的系统验证与人的接受不同；报告点评不自动构成接受发现或批准行动。材料回流、纳入讨论、正式采用是不同效果，必要时可以在一个清楚的业务审阅动作中表达多个效果，但不能用含糊“继续”暗中触发。

Fork／Subagent 保留已接受的独立来源、有界授权、停止和结果回流能力；模型检查只是模型意见，不是独立计算验证。下一纵切不因此获得自主派发、并行或递归 Agent 权限。

Data／Ontology 是基础权威，Hypothesis／Strategy 是受治理资产，Packs 是可执行能力，Knowledge／Memory 是背景能力。AI 可建议资产改进，不能静默提升为正式版本；Recall、Reuse、Learning 不互换。旧决定、预期和来源保留原版本，新认识追加修订。详情沿用[资产架构](../../architecture/asset-and-model-capability-architecture.md)、[数据权威](../../architecture/data-authority.md)和[安全边界](../../architecture/security-boundaries.md)。

### 4.1 能力总图与累计状态的使用

六＋二是完整产品覆盖图，§9 是主要模块及依赖图。唯一累计[能力清单](../capability-coverage/register.md)及其[最新全景视图](../capability-coverage/latest.md)承接产品范围；保留 40 个稳定 ID。前版[阶段建议 §7](xanthil-ai-led-analysis-next-slice-proposal-v0.1.md)是固定基线盘点，不再作为第二份可编辑累计状态。清单中的历史章节引用明确其蓝图版本，v4.1 规划映射与实现／验收快照分开呈现。

每项能力分别记录 **规划、实现、集成、验收**，各自带范围：规划表示有目标；实现表示有代码／机制；集成表示正式产品路径确实消费；验收表示在精确候选、输入与适用边界取得证据。四者不能压成一个“完成”勾号，也不能把局部已验收外推为全能力完成。没有核对的部分写未知。

产品经理负责能力定义及蓝图范围；工程接收后，Mini Engineering Controller 按[唯一维护政策](../../governance/product-change-execution-policy.md#blueprint-capability-coverage)更新交付增量、实现／集成／验收证据与快照。阶段验收展示全景。产品侧本次只补规划映射，不代写工程进度、不把静态评审升级为新的能力验收；同一分支和清单仍一次只有一个写者。

缺口必须影响决策：阻断阶段完整任务或核心安全／正确性的，纳入本期依赖；对本期结果无影响的，明确排除及返回点；是否有影响未知的，先做有界核对再排序。不能把“IR 只有记录”“报告未消费本轮证据”等缺口仅登记后继续增加无关故事。

## 5. 视图二：阶段路线与智能成熟度

产品形态 Personal → Team → Enterprise 与智能成熟度（分析助手、分析工作空间、领域智能、决策助手、决策智能系统）是两条轴，不是先把一列做满再进入另一列。

| 阶段 | 产品结果 | 推进依据 |
| --- | --- | --- |
| 0 随纵切形成共同基础 | 必要身份、语义、来源、执行与保存能力 | 当前任务能保存、重开、引用和检查，不先造全平台 |
| 1 Personal 可信且易用的分析 | 用户提需后，系统承担获准分析的推进与有用结果交付 | 正确性＋真实首次使用；001～003 已提供部分基础，不等于本项全部达标 |
| 2 Personal 决策闭环与重复价值 | 决定／预期、适用协作、结果回访、改进和下一 Case 采用 | 分别证明技术可用、独立完成、学习发生、学习有效和留存 |
| 3 Xanthil Team | 围绕已成立任务进行共享、复核、权限与共同复盘；专业配置有维护职责 | 多人真实需求、复用／交付、隔离／历史和团队成本／采用意愿 |
| 4 单场景企业试点 | 获准企业数据、必要 OSM、批准行动与结果回收 | 事前基线、Owner、护栏、接管／退出及可复查价值 |
| 5 Enterprise 扩展 | 按证据扩展身份、语义、连接、模型及多团队治理 | 各业务域、环境的独立风险与价值证据 |
| 6 有限域业务行动自动化 | 对已验证行动逐项扩大现实执行权限 | 专项授权、监控、停止／撤销、接管及适用回滚／补偿 |

**分析任务自动推进从 Personal 就要存在，不能等到阶段 6。** 阶段 6 扩大的是现实业务行动权限，不是允许 AI 开始做分析的时间点。后台维护自动化同样受其资产和权限边界约束。

阶段不是全量能力串行清单。Team 可在多人需求有证据时评估，不必等待每个长期结果成熟；也不能用工程测试、下载量或个别成功替代真实价值证据。

下表是重点顺序，不是五层全部串行，也不是自动排定五个 Change。每一项进入工程仍需自身正式产品输入、适用 UI 与权限；阶段 0～6 的长期能力不因此删除。

| 建设重点 | 交给用户的完整价值 | 共享能力与进入条件 |
| --- | --- | --- |

P1 三类验收共同通过后，可以讨论有界单场景试用。试用需另行明确对象、任务、来源、Owner、成功／停止条件、资源及数据／Provider／部署权限；此处既不批准试用，也不宣称已证明商业竞争力。企业环境必要的安全责任不能以“试点”省略。

数据、语义、反馈与专业能力可以围绕同一明确消费任务协同推进；没有实际阻塞时不把“先补平台”插在 P1 与结果回访之间。§6.3～6.4 的回访和下一 Case 采用是近期返回点，而非所有数据能力完成后的远期愿景。

### 6.2 推荐下一有限阶段 P1：AI 主导的会员复购分析交付

一个结果：**非技术运营负责人说出问题并提供获准资料后，由系统持续推进到经验证的发现、可点评报告与待审建议；用户判断、修改并选择下一步，形成明确的决定或暂缓／补证结果。**

[v4.0 阶段建设与下一纵切建议](xanthil-ai-led-analysis-next-slice-proposal-v0.1.md)保留原批准身份；其完整场景与验收建议继续复用，路线及采用状态以本版与批准记录为准。原文草案标签、技术评估尚待启动、累计清单初稿均是历史时点，不重新要求批准已确认方向。P1 是本蓝图中的阶段定位，不是 Change 编号、新状态机或开工令；不等于前文通用阶段编号。一个完整阶段可包含多个相互依赖的 Change，不将整个阶段强塞进单个巨大 Change，也不强拆为大量需用户逐次拼接的故事。

优先复用固定双 CSV 与现有复购方法，先解决一项真实支持的任务；不同时建设通用分析平台、全量后台管理、任意 SQL／Shell／Web、自主多 Agent 或企业权限。前台不要求用户逐项创建／拼接 Session、Run、Finding、Closure、Decision 等对象，也不以刚性聊天问卷代替表单。

本期任务族限定为双 CSV 上的 M1 总体复购比较、具备资格时的 M2 分组收入变化贡献、报告表达点评与合法期间调整后的重分析；不增加第二行业、任意人群筛选或因果能力。M2 的贡献不是原因证明。后台最少交付一个受验证、版本化并被这些任务变体真实复用的场景方法／口径配置；AI 在其中识别问题、追问关键歧义、调用受限能力和解释结果。不将“下降”预设为事实；不能支持的因果或策略效果明确拒绝，并给出可行下一步。

本期需显式修订未完成任务 AI 入口、任务级授权、待审建议和人工接受、Closure／首次正式决定次序等现行行为合同，并补齐场景内“语义／方法 → IR → 执行 → 验证 → 报告”的真实消费链。保留正确性、来源和人工决定；不是只重排现有页面。

本期完整设计一次说明任务范围、能力组合、依赖、授权、失败／修改、用户交付与三类验收；工程在稳定的产品语义下逐步细化实现，不预先冻结所有技术参数。共享核心可横向成组建设，有明确的本期消费者和退出条件，不为未来通用性无界扩张。

推荐三组建设：**语义／方法／IR 与受限执行验证组；任务协调／授权／恢复组；结果报告／点评／人的决定组**。前台任务路径贯穿三组，后台配置只覆盖当前场景的实际复用需要。正式接口和工程包边界交技术架构及开发流程职责评估，不以本图指定代码目录或部署结构。

下一验证纵切仍是“核实会员复购变化 → 理解证据 → 点评报告 → 选择下一步”，但它验证这一组能力是否贯通，而不是取代能力建设计划。尽早贯通受限真实链，每组新增后重跑相关路径，阶段末再做完整产品验收。完整设计不等于瀑布式最后集成。

#### P1 的复用与缺口判定

Desktop 已有真实存储、计算、验证、报告、决定与协作，不按“只有前端”重建。固定基线上的 Contract／Binding 参数确实改变计算；现有 IR 是固定计划记录与一致性校验，实际调用仍是预置管线。缺口是计划成为执行依据、未完成任务受控推进、一次明确人审整体正式生效，不是计算和存储从零开始。技术评审是静态依据，不是这些新能力已完成的证明。

当前建议按 A（空白任务到经验证发现／待审报告）→B（点评、重分析、完整恢复和最终人审）组织工程结果，具体数量及分包仍由工程按依赖决定。A 内尽早贯通真实 G1/G2/G3 消费链；A 的交付至少须具备停止、有效成果保存、重开不自动执行。确定 A 的任务、结果和持久身份合同时，先考虑 B 的整体人审提交边界，避免制造不能安全收尾的数据关系；不要求 A 提前交付全部 B，也不另设设计审批 Gate。

仅 A、单个 Change 或若干局部 PASS 都不是 P1 完成；完整 A/B 结果需在同一固定集成候选共同通过三类验收。替身可验证机制，不能替代真实 AI 质量和非技术用户体验证据。

### 6.3 紧接返回：结果回访与解释

取得有来源的行动回执及／或业务实际观察，对照当时的 Expected，区别“执行了什么”“观察到什么”“可以推断什么”。无执行、样本不足、口径变化、迟到数据、混杂及尚未成熟都真实表达；不把业务增长直接归因为所选策略。

用户主要提供系统无法取得的资料并判断评价，系统在权限内准备比较和提示缺口。不要求用户维护回访流程或填满不存在的事实。数据来源、回访触发、提醒／调度、观察窗口、指标及回执权威在本片产品决定中关闭；不从蓝图推定定时访问或通知权限。

### 6.4 再返回：改进与下一 Case 采用

从真实评价发现一个有价值的改进：例如方法限制、假设适用条件或策略禁用条件。交给正确 Owner，经验证／批准形成新版本；在下一 Case 明确展示其来源及适用影响，由业务使用者或已明确获准的资产管理政策完成采用，保留采用记录和旧链。

第一轮跨 Case 学习仍以**可见、显式的版本采用**为验收点，不将后台自动推荐等同于自动生效。普通业务用户不承担底层发布维护，但不得悄然替换其当前任务所依赖的口径或方法。学习发生与学习有效分开证明；不要求先建立全量资产发布平台。

### 6.5 个人闭环阶段评审

仍检查五类证据：可信分析与决定、适用预期、实际及有边界评价、正确 Owner 的改进版本、下一 Case 实际采用。新增共同问题：各环节是否由产品承担合理推进，用户是否独立获得价值？

逐行复核六＋二、未覆盖的三模式／DAME／OSM、后台维护负担及真实增长需要，明确下一消费场景；不以一项体验改进永久推迟这些目标。

## 8. Change 选择与 UI 前置规则

先选择有限阶段产品结果，再按能力依赖组织实现；不要求每个工程 Change 都是能单独售卖的小用户故事。横向共享核心 Change 合法，但必须说明当前阶段消费者、服务的完整结果、真实消费链及能力验收条件；不能以“做一层 Runtime／后台库”作为没有终点的目标。

每个 Change 的现有提案说明：服务哪个阶段目标、推进哪些能力、依赖哪些已交付或待交付结果、复用什么、这次增量怎样验证、还不能宣称什么。没有独立可用前台结果的能力 Change，以适用 UI Contract 展示其最终消费与可检查面，不虚构用户必须逐个验收内部模块，也不绕过现行每 Change 的 UI 前置要求。

工程仍小步、可测试、可回退并独立验证；产品阶段验收展示固定整合版本上的连贯功能组合。Change 的工程完成和适用用户产品接受照常履行，但不能累加为阶段完成。原有政策本就强调 result-sized package，并未强制把一切拆成微型故事；本次补充阶段目标、共享能力完成条件与整体验收，不把方法本身归因为已证实的根因。

后续每片仍绑定 change-scoped 高保真可点击 UI Contract 和用户 UI Gate。沿用有效 Xanthil 布局与 PX-004／006 模式，专业检查和协作能力保留；**专业六阶段不再被建议为普通用户必须逐页驱动的主任务路径**，这一变化须由新的 UI Contract 明确并获用户批准。聊天、卡片、图表或报告按任务选择，不预设“全改聊天”即成功。

首要交互验收是：用户提出需求后，系统能实际承担推进；可见有用发现、清楚的等待理由和可行下一步。不能仅用页面运行、按钮响应、节点隐藏或点击数变少验收。

已接受 UI 及历史规范原文保留；后续 Change 明确取代哪些可见行为及合同，保留哪些兼容路径。独立就绪审查、产品输入冻结、工程接收、连续 SDD/TDD、独立验证和用户产品接受遵循[现行执行政策](../../governance/product-change-execution-policy.md)，不恢复旧的强制角色流水线。

| 业务前台 | Xanthil 任务入口、资料提供、发现／报告、决策看板、结果反馈；上下文相关的“比较另一思路／检查反证”等入口；可展开证据与过程 | 让普通用户维护 IR、流程节点、语义映射和资产发布；把技术状态当业务成果 |
| 专业配置与维护面 | 方法／工作流、指标语义、数据连接与映射、假设／策略、Packs、权限／Provider／预算配置；按职责维护与版本化复用 | 每项分析都重新配置；用“后台”隐匿重要口径和权限；立刻造全量管理平台 |
| Application 任务协调 | 将需求和获准上下文转成可执行目标；跨能力推进、暂停／修改／恢复；调度模型与确定性服务，产生过程和结果记录 | 在 UI 中编业务规则；让 LLM 的自然语言承诺替代权限约束；双写运行权威 |

| Ports／Adapters／Profiles | 业务能力端口；Pi、模型、文件、SQLite、DuckDB、检索／网络等具体适配；部署 Profile 装配和约束 | 用通用工具无边界替代业务能力；把 Pi 当企业安全边界；自动选择第二 Runtime |

| Core 责任 | 关键内容与 v4.1 作用 |
| --- | --- |
| Semantic | 指标、对象、期间、上下文及绑定；复用后台定义并识别真正歧义 |
| Analysis | 假设、方法适用性、分析计划／IR、计算及证据判断；AI 不能以解释代替验证 |
| Decision | 备选、人的选择、事前预期、实际评价与责任／来源；不把生成草稿当正式决定 |
| Learning | 改进候选、Owner、验证与版本、后续采用和效果证据；不自动升级记忆为权威 |
| Execution | 获准执行、进度、停止／失败／恢复和审计；分析操作与现实业务行动分权 |

这些是逻辑职责，不冻结五套服务或模块目录。沿用 [Ports and Adapters](../../architecture/ports-and-adapters.md) 和 [Runtime 决策](../../adr/0003-business-runtime-port-strategy.md)：近期复用 Pi 适配与现有工具能力，不能从 AI 主导任务推导 Runtime 重写、第二 Runtime、注册表、热切换或通用接口。SQLite 运营状态与 DuckDB 分析数据继续分责。

### 9.2 IR 必须真正驱动执行，不只是前台之外的计划记录

业务需求与确认的关键意义 → Analysis Contract → 获准 Context／Semantic Binding → 版本化 Analysis Plan IR／执行约束 → 实际运行及适用独立验证 → 有来源的 Evidence／报告／待审建议。

IR 承接分析目标、输入、语义、方法、约束、输出及验证要求，必须实际约束执行。工程选择本片所需的最小表达及既有实现复用，不能只产出一段 JSON 给用户看；也不要求为本片先造通用 IR 平台、通用 Decision IR 或三套模式引擎。

本期能力完成的判据：运行前消费并验证适用的 IR 及其精确语义／输入绑定，由该计划决定受支持的方法、参数和依赖／顺序；执行及验证结果回链同一计划，报告消费该次证据。合法改变受支持计划内容，会改变实际执行选择／参数及适用输出；不支持或错配的内容被拒绝，不能悄悄回到固定预置流程。可经受控编译／物化为执行约束，不要求运行器直接解释某种 JSON 格式。

IR 不夺取 Contract、Data 或 Ontology 的权威；必须与其一致。严禁为证明“驱动”而允许任意代码或越权方法。本场景可以仅支持当前方法及明确参数组合，通用 DAG、任意 SQL／Shell、三模式引擎和方法市场不在本期。

同授权内的合法计划调整可以自动进行并留痕；改变业务范围、关键口径、来源权限或外部影响时须取得新决定并生成适用的新版本，不能原地改写已接受的历史。用户看业务含义和影响，专家可展开计划、口径、执行及验证记录。

P1 必须有判别性证据：同一合格输入选择 M1-only 时，两条计算路径均不执行 M2；选择 M1＋合格 M2 才执行分组贡献。数据含分组字段不自动选择 M2；“未选择”和“不适用”分别解释。改变合法参数必须改变实际读取／计算，忽略计划、固定参数或总是执行 M2 的实现应被验收识别。计划不支持、资格不符、版本错配、缺少强制独立验证时不能回退固定流程冒充成功；失败审计可保留，但不能产生相应成功证据或正式效果。

### 9.3 Fork、Subagent、Skill 的产品位置

它们服务用户任务，不是任务开始前必须理解的对象。前台在有价值时呈现“比较另一种解释”“检查这项建议的反证”“复用已验证方法”等业务入口，内部采用哪项能力须与其已支持范围匹配。

保留现有 Fork／Subagent 专业入口和可检查关系；下一片不把自主多 Agent 当必要条件。将来系统主动派发需另行定义权限、资源、停止、回流与采纳合同。Skill／方法可以是后台执行单元，但 Prompt 本身不是确定性规则、证据或数据授权。

### 9.4 静态技术评审的采用与职责边界

本次采用的方向是现有架构支持 P1，无需重新选 Runtime 或先建设完整数据／语义平台。三项业务接缝是“合格分析上下文 → 受限执行计划 → 已验证结果”；它们描述职责，不冻结新 API、Schema、数据库或独立服务。

- Application／执行器在准入、实际执行与结果发布处校验精确版本、资格、授权及真实结果绑定。这些是后台检查，不是要求用户连续确认三次。
- 同一任务的授权链及累计预算跨 Attempt／点评／失败／恢复保留；正常 Attempt 结束不必然使仍有效的任务授权到期。每次实际使用仍核验当前授权；主动停止、关闭／重开、过期与范围变化依已冻结语义处理，重开先恢复视图、显式继续，不能自动开跑或重置额度。
- 用户未选择给 AI 使用的点评不得先外发分类；原始列名、群组、语义文本与报告可能敏感，汇总或匿名化不自动获得披露权。实际出站规则和小群体保护在 P1 产品输入中关闭。
- 明确的人审动作须列出适用 Finding 接受、Closure／最终报告、Decision／Expected 的效果，并在产品承诺的整体提交边界生效；回应不明先读回同一结果，不能重复发布。仅保存分析不制造正式决定，补证不伪装接受。内部事务、身份、崩溃一致性由工程决定并实证；做不到则交用户调整承诺，不能静默恢复多个人工关卡。
- 两期筛选后全无有效行沿用资料资格阻塞，不生成该次 Finding、Closure 或 final；合格资料的一期分母为零与两期全空不同，前者按原合同表达证据不足而非零百分比。Expected 的适用护栏独立于依赖条件，需在审阅、保存与历史中可见；系统可准备可读建议，用户做判断，不要求先手填技术对象。
- 新计划／任务合同按兼容责任版本化；旧 CLI、Run、报告及 001～003 的原合同继续可读，不追补虚构 IR 身份、不强制迁移全部历史。未完成任务新增业务用例，不借此取消旧 Completed Assistant 资格或扩张 003 权限。

以上是需由正式产品包和工程合同落实、验证的约束，不是“评审完成即能力完成”。精确模块、函数、存储和验证机制留给工程；上层产品／数据／安全边界变化由用户决定。不新增跨 Controller 的日常技术签字环节。

## 10. 视图四：竞争价值与体验证据

### 10.1 竞争力是假设，必须证明

| 价值假设 | 用户实际获得的优势 | 最少需要的证据 |
| --- | --- | --- |
| 专业分析容易获得 | 不学内部流程就得到正确且有用的结果 | 首次独立任务、正确性与理解测试、投入／等待时间、与 Agent＋Skill 对照 |
| 领域能力可执行且可复用 | 不每次编 Prompt、定义指标、接工具和验算 | 真实消费方法与语义、适用性／反例、维护和重复任务成本 |
| 可检查的决策历史 | 找得到当时为何选、依据是什么、后来改了什么 | 精确版本、重开追溯、修订不篡改、用户能正确解释 |
| 有意义的比较与检查 | 容易检验不同解释和策略，识别反证 | Fork／Subagent 输出是否改变判断或降低遗漏；不是 Agent 数量 |
| 结果回收和解释 | 分开看执行、观察、预期与原因，指导下一步 | 有来源的实际、未知保留、归因限制、可行后续动作 |
| 经验复利 | 改进真实影响下一任务，并可能降低成本／提高质量 | Owner／版本／采用链、前后任务对照，学习发生与有效分开 |
| 团队和组织学习 | 知识方法能共享且责任清楚，不越权 | 多人真实复用、隔离、交付质量和维护负担 |

IR、Graph、Memory、Agent 或安全节点本身不是壁垒。若用户用一个 Skill 更快、更可靠且更省心完成相同任务，产品不能靠更复杂流程证明价值。用同任务、同数据、可比模型与权限预算比较人工／表格／BI／文档／Agent＋Skill；分别报告质量、人工劳动、成本、审计及复用收益，不选择性只报胜项。

### 10.2 继承基线、当前补充与证据边界

- **用户反馈**：Mac mini Change003 产品“起点不明、步骤确认多、帮助不足”；进一步指出应由 AI 推进任务、专业配置后移。
- **静态核对**：现行 Quick Assistant 只接合格 Completed Case；从空白分析仍需专业流程；主算和独立复算已经自动，不能说系统全无自动化；见[本轮证据索引](core-task-experience-evidence-v0.1.md)及其中 canonical specs。
- **历史画面**：已查看六张真实 Renderer 测试画面，状态／模型为合成输入，不是用户试用实录。
- **本次技术评估**：对固定业务基线及在研 P1 Candidate001 的静态评估支持方向；未运行产品、测试或 Provider，未核验 Mini WIP。见批准记录中的来源身份和采用范围；不能替代 P1 产品就绪复审、用户 UI Gate、工程验证。
- **未知**：当前用户的逐步实操、首次有用结果时间、独立完成率、实际人工操作量、真实模型建议质量及 Agent＋Skill 对照，尚未测得。
- **产品判断**：内部流程责任泄漏到前台是需要验证并改善的核心问题；不是据现有材料证明所有失败原因。

本轮早期 `core-task-experience-review-v0.1.md` 的路径简化和人工首次决定建议，以及对应 low-fi，仅保留为讨论历史；**不作为本版方向、冻结产品输入或下一 UI Contract**。其中有来源的观察继续可引用，不把其未获批准的提案当既有能力。

### 10.3 三类验收，在阶段产品上共同成立

| 验收 | 判断对象 | 不能替代它的证据 |
| --- | --- | --- |
| 场景 | 支持范围内从问题、资料到发现、报告和人的判断，含失败／缺证／变更的完整路径 | 若干故事分别演示、测试中直接预建最终状态 |
| 能力 | 语义／IR／执行／验证／报告等是否被实际消费，接口接通，范围及关键拒绝边界覆盖 | 文件存在、对象命名、日志有 hash、代码量或无判别性的单测 |
| 体验 | 首次用户能自然开始、在合理负担下持续获得可理解且可行动的帮助 | 按钮能点、自动化测试通过、操作数下降或文案更友好 |

三类验收复用现有规范、验证和用户接受记录，不再发明三套审批流水线。工程提交保持小；阶段接受必须面向同一固定集成候选，附完整能力清单、增量与剩余缺口。某类未通过时如实标注，不能以另一类 PASS 抵消。

先测当前产品基线，再预先确认目标、样本、数据和预算，不能看到结果后改阈值。分开测首次场景配置、首次任务和复用任务；后台隐藏维护劳动一并计入。原型动画、固定示例人数和演示额度不是真实性能／资源基线。

至少记录：首次使用能否独立开始／完成；首次有用结果的时间；用户必须完成的业务输入与机械操作分别多少；过程是否自主推进；结论、限制及下一步能否被正确理解；修改／失败后能否继续；授权、人工决定与审计是否保持。

“首次有用结果”是有来源、与问题相关且能支持继续行动的发现或具体数据缺口，不是欢迎语、计划、动画或重复问题。数据缺口提示与经验证业务发现分别计时，防止用快速报错冒充分析价值。只报告真实测量，先定观察方案和目标，再验证；机制测试、模型质量与人类体验证据不得互相代替。

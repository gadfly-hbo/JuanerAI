一、不要直接展示“三个核心”，要展示“三种专业能力”
可以先做这层产品语言转换：
底层核心	不宜作为默认界面的内容	应当让用户看见、操作的内容	希望用户形成的认识
Semantic Context Runtime	本体节点、Context Bundle、绑定规则等技术对象	指标口径、分析范围、定义来源、冲突提示、适用条件	“它不是只听懂字面意思，而是在确认我们讨论的是同一件事。”
Analysis Core / Analysis IR	原始 JSON、执行 DAG、内部调度结构	可编辑分析计划、候选假设、需要的证据、方法限制、计划变更	“它不是随便算一遍，而是在按可审查的方法解决问题。”
Harness / Execution Runtime	工具调用流水、进程日志、重试栈	真实进度、数据使用边界、暂停与恢复、检查结果、执行记录	“它做了什么我能查，哪里出了问题我能接管。”


关键不在于把技术术语换成中文，而在于让用户真正拥有这些操作能力。
例如，“分析口径已确认”只是一个标签；用户能点开口径、发现不对、修改并看到受影响结果，才是一项产品能力。
二、把能力嵌入一次分析中的五个关键时刻
我建议不要做一个专门的“核心三角展示页”，而是沿着用户完成任务的过程，让能力在最有用的时候出现。微软的 Human-AI Interaction 指南也是按首次交互、常规交互、出错时和长期使用来组织设计要求，而不只关注首次生成答案。Microsoft
下面用一个假设场景说明：
用户问：“最近四周老客销售下降了，是什么原因？要不要发优惠券？”

1. 分析前：让用户感受到“它发现了我没说清楚的地方”
不要马上输出一份长报告。先呈现一张简短的分析口径卡：
本次分析口径
销售指标：扣除退款后的净销售额。
老客范围：采用项目已确认的会员定义 v2。
时间范围：最近四个完整自然周。
比较方式：与前四个完整自然周比较。  
**需要确认：**当前数据同时包含“订单金额”和“净销售额”，二者不能混用。
操作：查看定义来源／修改口径／确认并开始。

用户不需要知道 Semantic Binding 是什么，却能够感受到：系统在计算前就拦住了一个可能影响结论的问题。
这张卡还应提供两个约束：
**来源可追溯。**定义来自用户本次确认、项目规则，还是已绑定的 Domain Pack，应当明确。没有依据时显示“待确认”，不能假装系统已经掌握企业标准。
修改范围可选择。“本次使用这个口径”不等于“将企业口径永久改成这个”。长期变更应另行提交审核。
这里的产品价值是少算错一道题，不是“系统检索了多少条知识”。
2. 开始分析：让用户感受到“我可以指导它，而不是只能等答案”
给用户一份可读、可改的分析计划，而不是只能观看的 Agent 思考过程：
准备怎样回答这个问题
先核验销售下降是否真实存在，再定位变化集中在哪些会员、商品和渠道；随后检查购买人数、频次、客单价和退款等因素，最后判断现有证据是否足以进入优惠券测算。
**当前限制：**尚未提供历史发券及核销数据，暂不能估计优惠券的增量效果。
操作：调整分析重点／补充假设／添加数据／确认计划。

用户可以说：
“先不要分析渠道，重点看高价值会员和退款。”

系统应当把这句话落实为计划变更，明确显示删除了什么、增加了什么，以及影响哪些输出，而不是回复“好的”后继续按原计划运行。
Google PAIR 特别强调：反馈不应只得到一句确认，还应让用户理解反馈会改变什么、何时生效，并保留编辑和控制的能力。Google Pair
这一步要让用户感知到的是：
“我不是在反复打磨提示词，而是在和系统共同编辑一份真正会被执行的分析方案。”

3. 执行中：让用户感受到“它在做具体工作，而且遇到问题不会失控”
不要把执行状态主要做成：
正在深入思考……正在进一步分析……正在综合判断……

建议改成与业务任务对应的状态：
销售变化复核：已完成。
会员分组比较：已完成。
退款归属检查：发现异常，等待确认。
优惠券效果评估：缺少数据，尚未执行。

当本地检查发现同一退款记录可能重复关联订单时，应当显示：
当前关联方式可能造成退款重复计算，相关步骤已暂停。
已完成的销售核验结果保留；退款相关结论暂不发布。
可以检查关联规则、提供新的映射，或取消这一分析分支。

这比“任务失败，请重试”更能体现专业性。
Google PAIR 对错误体验的建议也不是仅仅解释错误，而是提供继续前进的路径；交还控制权时，要让用户知道当前状态、下一步做什么以及怎样接手。Google Pair
对于你的 Local Code Analysis Mode，这一阶段还应该有简洁的数据边界说明：
计算位置：本机。
原始文件：只读。
发送给模型的内容：字段结构及本次获准的汇总结果。
外部发送记录：可查看。

这些说明必须反映实际权限和实际出站记录。只有“本地运行”的图标，却无法说明日志、异常信息和工具返回是否外发，不足以支撑对应承诺。
4. 结果出来：让用户感受到“这不是一段只能相信的文字”
我建议把关键结果做成结论卡，每张卡都能展开证据，而不是仅给报告末尾附一串来源。
例如：
发现：销售下降主要集中在某个会员分组。
**已完成检查：**指标复算、分组金额对账。
**仍然未知：**现有数据不能区分购买需求变化与商品供给不足。
**对决策的影响：**暂不足以据此支持全面增加优惠。
操作：查看证据／查看计算／提出异议／补充数据。

展开“查看证据”后，应当看到对应图表、数据范围、口径版本、方法说明、支持证据及反例，而不是另一段更加自信的解释。
不要把“代码执行完成”“数据检查通过”“原因判断成立”压成一个统一的绿色对勾。
尤其不要让模型随意生成“可信度 98%”。对 JuanerAI，我更建议首先展示具体的证据状态，例如“计算已核验”“方法前提未满足”“仍有替代解释”，而不是没有校准依据的总分。
目标不是让用户无限相信系统，而是知道何时可以依赖结果、何时应该保留判断。这也是 Google PAIR 所强调的“校准信任”，而非一味提高信任。Google Pair
5. 下一次使用：让用户感受到“上一次工作没有白做”
第二次分析，应当出现这样的体验：
发现可复用的历史分析方案。
可以沿用：会员定义、已确认的分析步骤、报告结构。
需要重新检查：本期数据完整性、商品结构变化、方法适用条件。
不会直接沿用：上次的数值结果与原因结论。

用户点击后，不用重新解释整个业务背景，但系统也不会把上一次结论复制过来。
这才是你“持续做出更好的决策”理念在界面上的一个具体落点：
复用的是经过确认的方法与经验，重新验证的是当前事实与结论。
假设库、策略库也不必一开始就让用户维护复杂的图谱。可以先提供“保存为待验证假设”“记录采用的策略”“补充实际结果”等贴近工作的动作。
三、最值得做成标志性体验的，是“改一个条件，看清整套分析怎样变化”
前面的五个时刻里，我尤其建议你重点打磨一种交互：
可控修改 → 影响预览 → 定向重算 → 新旧对照。

它能让用户通过一次操作，同时感受到三角的协同。
例如，用户在结果页说：
“把全部门店改成同店口径，看看判断还成立吗？”

系统不应该简单重新生成一篇报告，而应当显示：
首先，确认业务含义。
“同店”采用什么开业时长要求，是否排除装修闭店，以及两个比较期是否使用一致门店集合。
这是 Semantic Context Runtime 在发挥作用。
其次，说明影响范围。
哪些指标、图表、假设判断和报告段落会失效；哪些内容可以保留。
这是 Analysis Core / IR 在管理依赖与分析逻辑。
最后，受控执行并形成对照。
确认后重跑受影响步骤，保留旧版本，展示数值和结论的变化。
这是 Harness / Execution Runtime 在落实执行与记录。
用户最终看到的可以是：
更改后，结论发生变化。
原结论适用于全部门店；新结果针对可比门店。
部分下降来自门店集合变化，不能全部归为同店经营恶化。
操作：比较两个版本／采用新版本／保留原版本。

这里有一个重要工程前提：只有依赖关系和输入条件可以验证时，才允许复用未变化的计算；无法确认时应扩大重算范围，不能为了展示“智能增量计算”而冒险沿用旧结果。
我的判断是，这种交互比介绍“三角架构先进性”更适合作为产品演示的核心。因为用户亲手验证了：它不仅能回答，还能接受纠正，并管理纠正带来的后果。
四、前端应该是“一个任务工作区”，而不是三个技术控制台
针对 Xanthil Desktop，我建议在现有任务流程中组织这些能力，不另造一套平行产品。
主界面：围绕业务成果
任务顶部固定显示分析目标、口径摘要、执行状态和待处理事项。
中间主区域展示计划、图表、结论和决策候选。对话可以用于提出需求和修改，但不应成为保存任务状态的唯一载体。
按需展开：围绕专业审查
点击指标可以看定义，点击计划可以看方法，点击结论可以看证据，点击状态可以看执行记录。
专业分析师可以继续深入到 SQL、Python、数据血缘和验证详情；普通业务用户停留在业务说明层，也应该能完成主要任务。
**这是同一组事实的不同深度，不是为不同用户展示不同的“真相”。**会改变结论使用方式的重大限制，不应藏在高级设置里。
与 Report Studio 衔接：让可信度跟着成果走
用户将结论选入汇报时，应该同时保留口径、证据引用、限制条件和版本信息，但无需把全部执行过程塞进 PPT。
例如，正文保持简洁，附录提供分析说明；点击工作区中的对应观点，可以返回证据。
如果源数据更新，已确认的报告内容应显示“依赖已变化，待检查”，而不是后台静默重写。这样既保留分析可信度，也尊重你强调的人主导编审与内容锁定。

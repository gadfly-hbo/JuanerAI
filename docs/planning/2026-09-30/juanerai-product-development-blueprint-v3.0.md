## 1. 定位、版本及采用规则

JuanerAI 是从专业个人用户出发，逐步发展到团队和企业的
**Bottom-up Decision Intelligence System**。其产品主线是决策生命周期管理：
可信分析构成入口，让当时的依据、选择、行动与实际结果可追踪，再通过受治理的
改进影响下一次判断。记录、回访和审查的成本必须由实际价值证明值得承担。

初始用户仍是非技术业务／分析人员；会员复购诊断仍是首个冻结场景。
用户通过真实前端理解问题、依据、选择、预期、实际和下一步，不需操作源码、
JSON、IR 编译器、数据库或命令行。纯分析可止于有边界的洞察，不强迫行动。

### 1.1 为什么是 v3.0

沿用 v1.3 §1.3 的版本规则：兼容补充升次版本，非语义校正升补丁版本，
产品路线、目标用户、首切片、价值终点或核心验收边界的实质改变升主版本。
v2.0 将结果回访和后续采用推进到 Personal 阶段。本次在决定／预期与结果回访之间
插入受控协作，并将 Fork、受限 Subagent 放在同一产品 Change 内先后交付，
实质改变后续纵切顺序，故升至 v3.0。Personal 决策闭环的价值终点保持。
版本升级依据是路线调整，不是白皮书换版；v2.0 及其历史批准不被倒写。

白皮书仍是核心产品参考及商业化纲领；获批并完成整合的蓝图是产品开发执行指引。
白皮书更新须经用户通知、精确来源核对、逐项采用判断、用户批准版本化蓝图、
独立就绪审查及项目规则整合。任一步骤都不自动改写在研 Change。

本表沿用 v2.0 已批准的白皮书采用判断，按当前交付事实更新定位；v3.0 全文批准
不等于工程执行。“采用”不表示完整实现或立即实施；“延期”保留目标和回看条件；
“不适用”针对错误解释或当前纵切，不删除完整能力目标。

| 白皮书 v4.0 内容 | 蓝图处理 | 采用方式、延期点或禁止推导 |
|---|---|---|
| Bottom-up DI／Decision Lifecycle（§3–4） | 采用 | 用持续决策价值组织路线；可信分析质量仍是基础 |
| Case／Loop／Graph、System of Record、Lineage（§29–30） | 采用，分步交付 | Case 从问题开始；先持久记录及精确关系，再按真实查询需要扩展；不另建五套平台 |
| Personal → Team → Enterprise 及双轴（§25、27） | 采用 | Personal 对应 Desktop Free，Team 对应原 Workspace 产品；战略名称不自动改包名、接口、UI 或资产作用域 |
| Decision Record／Expected Outcome（§25.4、29） | 已采用，限定实现已交付 | Change 002 已补正式选择与事前预期及有界 Case Assistant；不把“优先验证”改标成已作决定，不代表完整 Decision Loop |
| Future Actual／Outcome Evaluation（§31） | 采用到个人阶段 | 无 Model Pack 也可回访业务结果；行动、观察、校准、归因和决策质量分别判断 |
| Outcome 驱动学习与下一 Case 采用（§20.6–20.7） | 采用到个人阶段 | 评价 → 候选 → 正确 Owner／验证／版本 → 显式采用；发生与有效分开证明 |
| 五类 Core（§13–14） | 采用为逻辑职责映射 | 语义、分析、决策、学习、执行复用既有边界；不预冻结服务、路径、Schema、数据库或工程拆分 |
| 双库与 Graph（§12、30） | 采用语义；规模化能力延期 | 双库保留独立 Owner、准入和版本；在个人跨 Case 查询评审及 Team 准备时复核扩展必要性 |
| Analysis IR／Semantic Context（§11、16） | 保留并明确位置 | IR 约束一轮分析执行与验证，Case 组织业务全过程；不增设通用 Decision IR，不把 IR 当独占壁垒 |
| Domain Pack／Model Pack（§18） | 保留并按消费需要扩展 | 领域决策方法可扩展；模型质量和业务决策效果各有验收；旧 Desktop 后启动 Model Pack 的顺序仍作废 |
| OSM／PIM、三模式、DAME、六条主线＋两贯穿能力 | 全部保留 | 按 §4 覆盖与回看，不成为并行造模块清单；普通 PIM 不要求 Objective／Gap |
| Report Studio／Deep Research | 保留，按需求选择 | 分别表达已有分析／决策依据、补充外部证据，不接管业务事实或最终决定 |
| 竞争与专业评估（§24、28） | 采用 | 领域深度、结果历史和学习是待验证优势；不以功能、架构或节点数量宣称优越性 |
| 企业 Graph／SSO／多租户／跨客户学习／自动行动 | 近期延期或无默认权限 | Team／企业试点或单项自动化提案时再评估；数据共享、训练、执行分别授权 |

六条主线的删减、场景更换或价值终点变更仍需用户明确决定；不能以本蓝图的
“先做最小闭环”解释为取消其余已批准目标。

## 2. 产品语义与共同边界

| 概念 | 产品责任 | 不等于 |
|---|---|---|
| Decision Case | 从问题开始保存身份、修订、责任、范围、依据及过程引用；内容逐步补齐 | 聊天标题、末尾报告包装、单次 Run |
| Decision Loop | Case 从问题到结果评价，再影响后续 Case 的价值过程 | 每个 Case 必须采取行动，或每次分析已闭环 |
| Decision Record／System of Record | 保存当时可见依据、备选、选择／不行动／暂缓及理由、责任和适用预期 | 正确答案库、Memory、行动批准 |
| Decision Graph／Lineage | 带来源、版本、时间及作用域的 Case／证据／资产／选择／结果关系 | 新事实真源、必须采用图数据库、同源材料多次独立佐证 |
| Expected Outcome | 观察前记录的预期、基准、窗口、护栏和评价安排 | 目标愿望、保证收益、事后补写的预测 |
| Future Actual | 在约定对象与窗口取得、有来源和质量说明的实际观察 | 预测、目标、LLM 推测、行动完成回执 |
| Outcome Evaluation | 区分执行符合性、实际观察、预期校准、策略归因和当时决策质量 | 指标上涨就证明策略有效；坏结果就证明当时决定不合理 |
| Recall／Reuse／Learning | 找回历史／检查适用性后复用／依据结果形成改进并用于后续任务 | 三者可以互换，或保存摘要即完成学习 |
| Fork | 用户从父对话选定位置及获准材料创建的独立讨论路径；人工选择结果回流 | 新分析 Case、数据快照、正式决定分支或自动回流 |
| Subagent | 用户发起的一项单层有界检查，有独立任务对话与精确授权，成功后自动回流待审结果 | 自主编排、递归派发、并行 Agent 群或独立事实验证者 |
| 子结果回流／采纳 | 回流供审阅；用户采纳将该结果版本作为有来源材料加入原父对话 | 自动外发、发布正式决定／预期／报告、接受 Finding 或学习生效 |

分析完成、作出决定、行动完成、结果评价完成分别表达；改进候选、批准版本、
实际采用和效果证据也分别表达。失败、不行动、暂缓、缺数及尚未成熟的结果均保留，
不补造成功，也不从评价样本中静默排除。旧决定和预期保持当时版本；新认识追加修订。
这些是产品语义，不是新增状态枚举或持久化 Schema。

Data 和 Ontology 的基础权威、Hypothesis／Strategy 的资产权威、Knowledge／Memory
的背景能力沿用[资产与模型架构](../../architecture/asset-and-model-capability-architecture.md)。
Case 记录“当时依据与责任”，不夺取外部交易事实、OSM 对象或资产 Owner 的权威。
Graph 的查询与摘要同样受源权限约束；失去授权不能借旧摘要继续暴露敏感内容。

## 4. 视图一：六条主线＋两项贯穿能力

| 范围 | 目标能力及完成证据 | 推进路径与明确回看点 |
|---|---|---|
| C1 业务双主线 OSM／PIM | PIM 完成独立调查；OSM 完成目标—差距—策略—行动—复盘；证据连接且权威不重复 | 保留会员 PIM 首切片及个人决策接续；个人闭环阶段评审时核对是否出现 OSM 需要，Team 准备与企业试点再复核；全量 OSM 非个人前置 |
| C2 三种分析模式 | 假设先行、深度研究、自主探索各有适用任务和独立正确性／拒绝证据 | 首切片假设先行；个人阶段每次选题检查澄清／证据／发现缺口；闭环阶段评审显式安排未覆盖模式；发现保持候选，不自动成为结论 |
| C3 产品矩阵与增长 | Personal 可持续使用，Team 多人复核复用，Enterprise 治理及场景价值 | 按 §5 推进；每次阶段评审检查留存、协作需求、使用负担与迁移；CLI 伴随与其他平台适配通过实际需求另定 |
| C4 方法与能力扩展 | DAME 描述、诊断、因果、预测、探索、优化均在支持场景有适用性、独立验证和限制；Packs 提供版本化可执行能力 | 随 §6 消费者需求扩展；个人闭环评审逐一核对六类方法缺口及下一消费场景；本地 Model Pack 与 Enterprise Serving 分别准入，不以留存追加模型技术 Gate |
| C5 决策与价值验证 | 证据支持可审查选择；预期、批准、回执、实际、评价可区分；允许未知 | 首切片只到分析／候选；§6.2 记录决定，§6.3 补受控协作材料，§6.4 回访；个人阶段即有受限结果评价；企业接入与自动行动另行授权 |
| C6 资产积累与能力进化 | 结果形成有归属的候选，经验证／批准成新版本；下一 Case 显式采用且历史不变 | §6.5 先一种有需要的改进及 Owner；个人闭环评审检查真实采用；Team 准备时核对分享／迁移，企业试点核对组织治理 |
| A 数据、语义与执行 | 问题经 Contract／Context／Binding／IR 约束真实计算与证据，精确版本及来源可追踪 | 复用首切片及既有 Core／Ports；每个纵切检查数据资格、口径可比、权限和历史重放条件；来源或执行边界变化单独决定 |
| B 可信治理与人的责任 | 支持与反证、适用裁判、不确定性、隐私、审批及独立证据可见且受约束 | 最低可信性从个人版存在；随分析、决定、结果与学习补齐对应检查；不能等收费／企业阶段再保护数据与证据 |

阶段评审在现有规划中逐行记录“已验收行为及证据、未达目标、下一候选、依赖、回看点”。
本稿不把任何完整行标为已实现。§11 的 Demo 是限定范围的研究参考，非整行完成证明。

单用户，在 C4 复用现有只读能力，在 C5 补充可审查材料，在 C6 保留来源但不发布
资产；A 增加精确父子及回流关系，B 约束独立授权、顺序执行、停止和人工采纳。
OSM、其他模式、Team、方法／Packs、Actual／评价及跨 Case 学习仍在各行返回点评审。

## 5. 视图二：产品形态、成熟度与阶段路线

产品形态回答使用者及治理范围，智能成熟度回答已能完成的价值过程。
Personal／Team／Enterprise 与分析助手、分析工作空间、领域智能、决策助手、
决策智能系统是两条轴，不是把一列做满才准进入另一列，也不与自动化权限等同。

| 阶段 | 产品结果 | 推进所需证据 |
|---|---|---|
| 0 随纵切形成最小共同定义 | 复用必要身份、版本、Case、Contract／Context／IR、来源和边界 | 当前任务可保存、重开并准确引用历史；不先做全平台 |
| 1 Personal 可信分析 | 完成现有非技术用户会员复购诊断及候选比较 | 原冻结产品输入的真实 UI 技术验收；用户价值研究另行授权 |
| 2 Personal 决策闭环与重复价值 | 决定与预期之后，先受控协作，再结果回访、改进及下一 Case 采用 | §6 五项闭环证据；分别报告技术可用、真实使用、学习发生、学习有效和留存 |
| 3 Xanthil Team | 围绕已成立工作流共享 Case／语义／方法、复核、权限及共同复盘 | 真实协作需求、多人复用与交付、历史及权限隔离、团队成本和采用／付费意愿 |
| 4 单场景企业试点 | 获准企业数据、必要 OSM、批准行动与结果回收 | 预先确定基线、Owner、范围、护栏、接管及退出条件；可复查价值报告 |

### 6.3 当前选定纵切：受控 Fork 与单个 Subagent 协作

**完整用户任务：** 在来源有效的根 Case Assistant 中，用户选择一条已有讨论路径
分叉比较另一个解释／候选，或明确交给一个 Subagent 检查反证与限制；在独立子对话
查看运行和来源，将结果回流、审阅并决定是否加入父对话材料。正式决定仍由用户
按 Change 002 原流程审阅和发布。

[已批准讨论稿](xanthil-fork-subagent-product-proposal-v0.1.md)是本次范围与行为细化输入；
本节给出完整路线边界，详细验收与可点击场景由同目录的正式产品计划及 UI Contract
承载，二者的全文／UI Gate 已获批准，尚未工程接收。本片按同一 Change 内先 Fork、后 Subagent 交付：

- 入口仅为来源仍有效的根 Case Assistant，关联当前 Completed 专业 Case revision、
  accepted Finding、有效 Closure、final report 和正式决定基线。子对话不再创建下级
  Fork／Subagent；不新建分析 Case 或复制原始数据。
- Fork 选择已保存分叉点、明确所选历史／报告、获准聚合数据与讨论目的，建立独立
  子窗口。继承材料显示来源；父后续新增消息不自动进入子上下文。用户选择已完整
  保存的结果，人工回流到原父对话；不会默认返回全部历史。
- Subagent 是用户发起的单层、单个有界任务，独立窗口允许在自己的授权范围内
  追问用户。只有完整、校验通过、已保存的成功结果才自动回流一次待审项。
  失败、停止、超时、预算耗尽或 Interrupted 不产生成功项；同源模型意见不是
  新业务数据、独立验证或因果证明。
- 本地创建不调用模型。每次子任务独立预览和确认来源、精确所选材料、自由文本、
  Provider／Model、五类既有只读业务能力、轮次／运行时间／等待截止／费用边界。
  父授权不传递为子授权；未选历史、其他 Case、原始行和新的工具权限均不可读取。
- 模型任务顺序执行：父 Attempt Running／Waiting 时先明确结束，才可启动子任务；
  不隐式停止、排队或后续自动启动。子运行时父可查看，父继续模型工作需新的授权
  和 Attempt；一次只运行一个模型任务，不做递归、并发或自主派发。
- 回流只产生带子身份、结果版本、来源 revision／范围和状态的待审项。采纳须绑定
  用户实际查看的精确结果和版本，只加入原父对话材料；拒绝保留来源与历史。
  不直接写 Evidence／Finding、正式决定／预期或报告，不替换原草案。
  采纳不会启动模型；父后续外发仍需选择材料并重新精确授权。
- Case revision、授权数据或正式决定基线变化时阻断执行／回流／采纳；历史保持
  原来源并显示过期，不迁移到 latest。父后续消息本身不使已冻结的子上下文过期。
- 同一结果的回流／采纳不得重复创建父材料；失败不留下可见半成功。成功但回流
  失败保留子结果，用户可本地幂等重试；不重跑模型。重开后待回流恢复也只由用户
  明确触发，且重新检查来源和父对话资格。
- 视图切换是导航；明确关闭子窗口会中断其活动任务并使待用授权失效；关闭父会话
  须说明并中断该关系下未结束的子任务。停止赢过迟到输出。应用重开将遗留运行／
  等待态显示为 Interrupted，不恢复 Pi session、不自动重发模型请求。保存历史、
  已成功结果及已回流／采纳／拒绝关系保留。

**验收终点：** 用户在正常原生 UI 完成两项真实协作路径，能辨认来源、独立授权、
运行与回流状态、待审与采纳区别；负例证明范围拒绝、顺序执行、停止／迟到处理、
失败重试、过期阻断和重开保持。真实 Application／持久化／Adapter 契约及原生路径
需各自证据，静态 UI、测试替身和真实 Provider 验证的证明范围分别报告。
具体 Provider 验证仍需另行授权数据、模型、预算和命令，本文不授予调用权限。

**非目标与返回点：** 不做通用 Quick、其他分析模式、Web／Shell／任意文件／SQL、
跨 Case 继承、新工具、Prompt 编辑、自定义 Skill、第二 Runtime、后台自主运行、

### 6.4 协作之后：结果回访与复盘

**完整用户任务：** 回到前次决定，说明获准的线下行动实际发生了什么，导入或记录
有来源的实际观察，对照原预期和护栏，形成有边界的复盘及后续建议。

- 首期可人工记录已有线下行动及导入结果；这是记录机制，不是许可执行真实行动。
  人工声明必须显示来源／可信等级，不能冒充独立系统回执。
- 决定记录、行动批准、实际执行与回执、Future Actual、评价分别保存和呈现。
  没有独立证据时，只能报告实际具备的证据等级。
- 观察须核对对象、指标口径、时间窗口、数据来源、覆盖／缺失和成熟度。
  未执行、未到期、失访、缺数、口径漂移与护栏失败保持可见，不能默认成功。
- 复用新数据修订、计算、来源及报告基础；补足 Expected／Actual 对应关系和资格
  检查。原 v1.3 的周期重跑／版本比较候选转为这里可复用的增量，不是独立默认首选。
- 区分执行偏差、实际观察、预期校准、策略归因和决策质量。无适用对照／评价设计时
  明确无法归因；结果改善不等于策略增量。迟到数据／更正追加观察或评价修订。
- 验收包括合法观察与复算、尚未到期／缺数／不匹配拒绝、回执与效果不混淆、
  历史预期和原评价可读、以及不因复盘自动启动下一行动。

**当前边界：** 不要求自动触达、全量 OSM、企业连接器或新模型训练。当前冻结方法
不被假定足以评价任何策略效果；场景需要新方法时，由明确需求单独确定范围。
真实用户、业务数据、行动和结果访问仍需分别获得对应权限。

### 6.5 再后：改进与下一 Case 显式采用

**完整用户任务：** 从一次有来源的结果评价提出一个具体改进，交正确 Owner 验证与
决定，形成可识别的新版本；后续适用 Case 明确采用它，并比较分析或选择的变化。

- 先选择一种当前确有需要的改进类型，例如假设适用条件、反证要求或方法规则；
  其类型和 Owner 在该纵切产品输入中明确，不一次实现所有资产后端。
- 复用 Owner、Context Commit／Teach 的语义：候选可被拒绝，验证不足不发布；
  已批准版本不自动采用，推荐也不改变旧 Case。
- 后续 Case 保留来源评价、批准版本、适用性、采用／未采用原因及真实变化。
  旧 Case 按原版本可读；同一 Case 的一次重跑不能冒充跨 Case 采用。
- “学习发生”需要可追踪采用及分析／选择改变；“学习有效”还需在独立留出或后续
  可比任务中继续检验质量／效果。结果未成熟时只声明已发生，不声明有效。
- 验收覆盖正确 Owner、候选拒绝、未批准／不适用版本拒绝、显式采用、旧历史不变，
  以及不能把未来结果泄漏进原决定或独立评价材料。

**当前边界：** 不自动训练、更新全部假设可信度、改变 Ontology、发布 Pack 或跨客户
共享。可先形成最小来源关系和查询，完整 Graph 服务不是该用户任务的前提。

### 6.6 Decision Loop MVP 的完成判断

在一个明确角色和可观察结果的场景中，共同验证：

1. 真实问题形成具有责任、范围和版本的 Case；
2. 分析依据来自真实受控计算、验证和可追踪证据；
3. 证据支持可审查 Options，或明确不足以建议；
4. 决定与事前预期接续适用行动证据、合格实际观察和有边界评价；
5. 结果产生经治理的改进，下一 Case 显式采用并检验变化及后续效果。

只完成前几项仍可有独立用户价值，但不宣称整个 MVP 完成。尚无后续结果时，
可以验收学习接续的软件行为，不可宣称真实学习效果。纯分析任务和适用决策闭环
分别统计。合成 UI／Demo 只能证明限定流程，不能补造真实经营闭环。

|---|---|---|

| Decision Core | Case 过程引用、Options、Decision Record、Expected／Actual 关联及 Decision Lineage | OSM 仍拥有目标、策略组合、行动和经营 Review；业务决定／行动 Owner 保留责任 |

### 9.2 IR 仍是分析执行与验证合同

```text

→ 获准 Context／Binding／能力版本 → 确认 Contract／Analysis IR
```

IR 表达本轮分析怎么执行、验证和交付，执行必须真正消费它；不是装饰性 JSON、

历史依据绑定当时数据／语义／方法／模型身份，不用 latest 改写过去。
缺匹配输入或环境时说明不能精确重放，不保证相同 LLM 输出或未获准的通用恢复。

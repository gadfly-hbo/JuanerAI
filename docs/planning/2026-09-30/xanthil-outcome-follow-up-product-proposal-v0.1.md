## 2. 推荐切片与明确返回点

**推荐先交付一个本地、确定性为主的会员复购结果回访。** 从一个已正式采纳的决定／预期版本出发，完成一次可核查的观察与人工确认复盘。现有运行能力全部延续；不为本片增加通用指标平台或新的 Runtime。

用户最终拿到：

1. 固定关联原 Decision Record、Expected Outcome 和分析 revision 的行动情况记录；
2. 有来源、质量与成熟度说明的实际观察；
3. 原基线、原预期、实际数值、可比性及护栏核对；
4. 经用户确认的复盘结论及报告新版本，能在重开后准确读回。

首个验收场景建议选用原 Case 中一条已采纳的会员复购运营候选，行动由用户在线下执行、在产品内记录。最终具体候选和行动种类在产品冻结前指定，不编造候选、假定行动已获批准或默认真实经营结果。

不行动／暂缓也能回访：记录是否仍未行动、重评触发条件是否出现及依据；Expected Outcome 不适用时不强迫填写效果数值。

本 Change 结束后再规划“从复盘产生一种有正确 Owner 的改进，并由下一 Case 显式采用”。本片可以保存后续建议，但不会直接发布资产、改写 Skill／Prompt 或把建议标为已学习。

## 3. 建议的用户流程

### 3.1 选定要回访的决定

用户在专业模式阶段 6 的正式决定／历史区域点击 `结果回访`，选择具体 Decision Record／Expected Outcome 版本。显示当时 Case revision、决定、预期、报告、责任人与时间。

允许回访仍可读的历史正式决定。新决定出现时提示“当前决定已更新”，已有回访继续关联用户选定的历史版本，不自动换成 latest。Quick Assistant 可提供返回该回访的导航和已确认摘要；来源仍由正式业务记录决定。

### 3.2 确认观察约定

用户逐项确认本次要检查的对象、指标、原基线及来源、观察窗口、预期适用性、护栏、结果来源／Owner 和评价责任人。界面同时展示原 Expected Outcome 的文字。

这是对原文字的显式对应和补充说明，不改写原预期。每项说明保留确认时间与原始来源。若原预期没有可量化方向／范围，系统保留“原预期不可量化”，可报告实际观察，但不能补造一个已达成目标。

原预期的保存时间不等于“实际结果已知前”。用户还须声明该预期形成时是否已知本次实际结果，记录最早知悉时间及依据；只有人工声明时明确标级，不冒充独立时间证明。原预期形成在已知结果之后、先后关系未知，或关键目标在结果已知后才补充时，均标为“事后／时序未核验”，只允许描述性观察，不产生事前预期达成／校准结论。

后续指标对应也保留独立时间；仅解释原已明确的对象、口径、窗口和目标，不倒写成当时已有的量化约定。实际已知后新增的阈值、观察对象或范围只作为事后说明。未确认对应关系，或原文不足以支持该对应时，不产生“符合／不符合预期”的正式判定。

### 3.3 记录实际行动

建议支持 `未执行`、`部分执行`、`已执行`、`未知` 的用户可见区分，记录行动说明、执行者、时间、偏差以及来源。

首期只有人工填报及外部批准／回执的引用信息，明确显示“用户声明”及填写人、时间；不验证任意文件或连接外部系统，不生成行动批准或冒充独立系统回执。没有批准或回执证据时，报告相应缺失，不替用户推断合法批准／完成。

未执行或未知时可以保留经营指标观察，但不能把变化解释为该行动的结果。

### 3.4 导入并核对结果数据

推荐复用 `members.csv`／`orders.csv` 的列映射、质量问题处理、快照确认和来源指纹，并复用 DuckDB 主计算与 Python 独立复算。首期继续使用既有 CNY、Asia/Shanghai 和有效订单口径。

适用的现行产品合同为 [Desktop spec](../../../openspec/specs/xanthil-desktop-decision-case/spec.md) 的 REQ-XDESK-004／005：数据准入、确认和复购计算语义复用，而结果回访拥有独立业务身份，不复用原假设判定作为行动效果结论。

结果观察拥有自己的批次和修订身份，引用原分析、决定／预期及新快照。它不替换原分析快照，不将回访数据自动变成原 Case 的新分析 revision，也不改变旧 Assistant 的来源、草案或当前正式决定。

推荐首个可计算范围：

- 主指标：既有“期间活跃会员复购率”；期间内至少一笔有效订单为活跃会员，至少两笔为复购会员，复购率为复购会员／活跃会员。必须显示分子、分母和精确计算依据。
- 可选数值护栏：既有“复购收入”，即每个会员按支付时间及现有订单 ID 排序规则排列后的第二笔及之后有效订单之和，不是总收入或活动增量。其他护栏只能保存有来源的人工核对或未核验状态。
- 原基线期与观察期遵守既有两个等长、不重叠的半开日期区间；不默默放宽期间、时区或人群口径。
- 对象为现有计算所支持的期间活跃会员范围，不冒充固定实验队列或某次活动触达人群。

基线必须由原 Expected Outcome 的依据明确指向原分析的一个已验证期间及指标；用户显式确认该对应，不默认选择原分析的 current 或 comparison。没有可唯一确认的原基线时，可记录观察，不能进入合格预期对照。

首期推荐新导入的一对 CSV 同时覆盖选定原基线期和后续观察期，由来源责任人声明两个期间的覆盖、截止与缺失，并进行双引擎核验。仅包含后续期间的数据不能满足此完整对照路径；缺少历史覆盖不等于历史零订单，也不直接当作基线漂移。两期均声明覆盖且通过核验后，新基线与历史已验证基线相同才允许继续可比评估；若不同，显示数据更正／口径变化并阻断普通可比评估。历史值不被新结果覆盖，本片不自动改换基线以恢复可比。

### 3.5 确认资格与有边界评价

显示并核对源身份、对象／范围、指标定义、期间、数据截止、完整性声明、覆盖／缺失、验证结果及护栏。数据截止和完整性声明需有明确来源责任人；日期已经过去或数据存在某条订单，均不足以证明观察完整。

建议分开呈现：

| 评价部分 | 首期可以确认的内容 |
| --- | --- |
| 执行符合性 | 人工声明的实施情况、偏差及证据等级；缺独立回执则显示缺失 |
| 实际观察 | 经双引擎核验的期间数值、变化及质量／成熟度 |
| 预期对照 | 原预期与合格实际的方向／范围对应；缺可量化预期则不能判定 |
| 护栏 | 有来源核对、触发或尚未核验，不能把未核验写成通过 |
| 策略归因 | 本片默认“无法由期间对比归因”，不输出策略增量或显著性结论 |
| 当时决策质量 | 展示当时依据、备选和限制供人工复盘；不依据好坏结果自动评分 |

尚未到期、覆盖不足、校验失败、口径不匹配和零分母均有独立可见原因。建议明确区分三类正式输出，用户确认不会提高数据的证据等级：

1. 数据通过双引擎核验且对照资格完整：可追加合格实际观察、有限预期对照及复盘报告；仍不能归因。
2. 数值通过双引擎核验，但成熟度、覆盖、时序或口径不满足对照资格：只能追加带限制的观察与“目前不能判定”评价；不标为合格预期对照。
3. 数据未通过验证、未提供，或来源不足以支持可信数值：只能追加行动／缺失状态、“目前不能判定”评价及报告；没有正式可信 Actual 数值，失败计算也不因确认而发布。

覆盖不完整的数值至多是“本次已提供数据内的观察”，不冒充完整期间总量。允许如实记录未知是建议的产品行为，待用户批准。

### 3.6 保存与更正

用户检查来源、评价、限制和后续建议，明确点击 `确认复盘`。成功时按 §3.5 的资格追加本次允许的观察或缺失状态、评价正式版本及复盘报告，不强制生成 Actual 数值；失败保留草稿并给出安全重试，不显示半成功，重复提交只确认一次。

复盘报告关联固定的原决定报告及本次观察／评价，不移动当前正式决定指针，也不把历史决定冒充当前决定。旧决定、原预期、原分析、旧报告均保持可读。

迟到数据、数据更正或评价更正均创建追加版本，记录更正原因、时间、责任人与先前版本；旧观察和旧评价保留。结果进入之后的新预期说明注明事后时间，不倒写原预期。取消未确认编辑不追加正式版本。

## 4. Agent 和确定性能力的建议分工

推荐第三 Change 的核心回访不新增模型调用：数据确认、计算复核、资格判定、版本与采纳全部确定性执行，复盘解释及后续建议先由用户填写。第二 Change 的 Agent、多轮、Provider 接入和原三类辅助继续可用，其既有工具和外发范围不因回访数据存在而扩大。

若用户选择在本片加入 `帮我复盘`，建议只做一次只读模型辅助：逐次展示原决定／预期、已确认观察摘要、可比性与限制，模型只起草解释，用户编辑并确认；不生成 Actual、不判定因果、不自动确认复盘。它需要正式补充范围、精确 payload、失败手动路径及 UI 场景后才能冻结，不能直接复用旧授权。

Fork、Subagent、自定义 Skill、Prompt 编辑、Web、Shell、任意 SQL、任意文件访问和行动执行继续按既有边界处理。本片不重新选择 Runtime，也不扩大成通用自主复盘平台。

## 5. 增量 UI 方向

沿用第二 Change 的品牌、视觉质量、三栏关系和 PX-004／006 工作台；保留专业六阶段名称。新增入口集中在专业阶段 6 的正式决定／历史区域，建议回访内容按 `观察约定`、`行动情况`、`实际结果`、`复盘报告` 展示，不另造产品壳或新的第七分析阶段。

主区域优先展示原预期与实际对照，右侧继续承载来源、质量、限制与报告版本。任何缺数／不可比／用户声明／无法归因状态都有文字标签；关键确认、取消、更正及版本差异须可操作。Quick 仅提供明确回到专业回访的入口和正式摘要。

正式产品输入前需制作本 Change 的高保真可点击增量 UI Contract，覆盖正常回访、不行动／暂缓、未到期、数据不匹配、未知、护栏问题、确认失败、迟到更正和历史决定路径；取得用户 UI Gate PASS。本讨论稿没有 UI Gate 结论。

| AC-10 | 正常 UI 支持键盘、焦点、来源打开、版本对比和重开；无新行动、通知、学习发布或默认模型外发副作用 |

正面证据应包括真实本地计算和独立复算；合成数据可用于软件验收。真实业务效果、长期回收率、学习效果和策略因果结论需独立研究与授权，不能由此工程 PASS 推导。

首期至少验证以下边界场景，具体夹具和工程步骤留给接收后的工程设计：

| 场景 | 应有结果 |
| --- | --- |
| 两期完整、双引擎一致、重算基线与历史相同，原预期时序及对应已明确 | 允许有限对照；结果仍不是行动因果效果 |
| 只有后续期间数据，没有历史覆盖声明 | 显示历史覆盖缺失；不把空历史当零或直接宣称漂移，不产生合格对照 |
| 原预期虽早于当前导入，但用户当时已知结果或无法确认先后 | 只作描述性观察；不能声称事前目标已达成 |
| 双引擎数值一致但观察未到期／缺覆盖 | 可确认受限观察和未知评价，不能发布完整期对照或成功效果 |
| 导入校验失败或双引擎不一致，用户仍确认未知复盘 | 可追加缺失状态及报告，不发布失败计算数值为可信 Actual |

Product Core 拥有回访资格、预期／实际关系和评价边界；Application 拥有确定性流程、确认与版本追加；业务 Ports 表达所需数据／计算／存储能力；现有 Adapter 执行物理操作；Profile 组合；Desktop 表达用户控制。遵循 [数据权威](../../architecture/data-authority.md)、[安全边界](../../architecture/security-boundaries.md)、[复杂度控制](../../governance/change-complexity-control.md)及[复用基线](../../governance/xanthil-first-slice-reuse-baseline.md)。

产品不预定 TypeScript 名称、表结构、文件路径、事务机制或新的包／服务。持久化和兼容性影响由 Mac mini 在接收后决定并验证，保留既有 Product Core → Application → Port → Adapter → Profile 和 Pi 隔离边界。

价值假设：一次正常 UI 回访能减少用户在表格、聊天和报告之间寻找“当时预期与后来结果”的成本，同时避免无依据效果宣称。需要观察用户能否独立完成、识别不可比与证据等级、准确重开更正历史，以及记录负担；本稿不编造效率或成功率阈值。

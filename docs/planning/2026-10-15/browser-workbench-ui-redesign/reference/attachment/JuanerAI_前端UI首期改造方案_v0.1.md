## 1. 首期结论

建议以现有 Xanthil Desktop 为基础做增量改造：**对话启动，依据按需展开，成果集中处理；同一个任务始终共享同一份业务状态。**

本期的目标不是把 JuanerAI 做成通用办公 Agent，也不是复制 PilotDeck 的全部功能，而是降低业务分析与决策人员的操作负担，让用户能够清楚回答：

“我正在分析什么？”“这条判断依据是什么？”“现在需要我确认什么？”

以三个界面状态组织工作：

**对话状态 → 辅助审阅状态 → 成果工作状态。**

它们不是三条独立流程，也不是三种分析方法。自主探索、假设先行、深度研究的底层方法与推进方式保持原样；简单／专业模式也只调整信息披露深度。

### 1.1 本次边界

| 本期做 | 本期不做 |
|---|---|
| 入口、导航、布局、信息层级与交互反馈 | 替换 Agent 底座、迁移技术栈或整仓 Fork |
| 对话、依据面板、成果区的切换与状态保留 | 重写 Semantic Context Runtime、Analysis IR 或 Harness |
| 发现卡片、待确认事项、来源与口径展示 | 新建后台记忆、模型路由、Always-On 或自动化系统 |
| 数据行／报告文字引用到当前对话 | 完整电子表格编辑器、IDE、终端或 Git 工作台 |
| 报告单一主稿、锁定事实、局部改写提案 | 建设完整 Report Studio、PPT 排版或 Office 编辑套件 |
| PC 优先的静态 HTML 原型与基础窄屏回退 | 将移动端列为首期产品交付目标 |

**不修改现有开发模式、工程门禁、代码仓库或已实现的业务流程。** 本次未审阅 JuanerAI 最新前端源码与最新 UI Contract，因此下文是待映射的目标交互，不是对现有实现缺口的断言。

## 2. 六项借鉴与 JuanerAI 的具体改造

### 2.1 对话成为默认工作状态，而不是一个功能页签

**借鉴重点：** 用户先表达工作意图，再由任务上下文决定展示什么能力。

**JuanerAI 改造：** 首页保留项目与最近任务，中央突出业务问题输入框，输入框旁提供“添加数据”。给出一个完整、可体验的业务案例，而不是罗列 IR、模型、指标库、假设库等技术入口。

用户可以先问问题，也可以先添加资料。首次打开不要求配置分析框架、选择方法库或理解内部资产结构。已经存在的任务从左侧恢复，避免把每次追问变成新任务。

**本期界面：** 左侧项目导航 + 中央对话启动区 + 明确的数据入口。模型选择不占据最醒目的位置；正式产品如保留模型设置，应放在现有设置或高级入口。

**Demo 对应：** 首页、新建分析、最近案例、新建本页项目、文件选择与拖放。

**验收重点：** 用户无需理解架构名词即可进入案例；查看资料后返回首页，未发送问题不能丢失。新建项目不能悄悄改变既有任务的数据范围。

### 2.2 对话、辅助面板与成果工作区各有职责

**借鉴重点：** 展示重点随工作需要变化，而不是不断增加相互竞争的窗口。

**JuanerAI 改造：** 对话负责委托、澄清、推进与反馈；右侧依据面板负责查看证据、口径与过程；成果工作区负责集中查看数据、图表与报告。

在宽屏上，“对话 + 依据”左右并排。进入成果区后，“成果 + 紧凑分析助手”并排。助手使用原任务，不新建第二个会话或第二套业务状态。

同一时刻只有一个辅助审阅面板。成果模式中需要深看证据时，回到“对话 + 依据”，关闭后仍能继续阅读原成果。首期不实现自由拖拽浮窗、任意分屏或同时打开多个检查器。

**Demo 对应：** 顶部“对话／成果／依据”；依据面板的关闭与宽度调整；成果中的同一任务助手；不足宽度时按需展开助手。

**验收重点：** 切换不清空草稿、已选上下文或报告修改；往返后恢复相应阅读位置。报告不能在聊天、文件预览、编审页面分别出现独立可写版本。

### 2.3 成果是可操作对象，而不只是下载链接

**借鉴重点：** 让用户围绕成果继续工作。

**JuanerAI 改造：** 将重要 Finding 展示为发现卡片，至少包含结论摘要、关键数字、证据状态、适用边界与下一步动作。卡片操作收敛为“查看证据／引用追问／加入报告”。

数据结果、图表与报告都归属于当前任务的成果区。已加入报告的发现保留引用关系，不因修改报告表述而改写源 Finding。导出是成果区的一个操作，不是工作流的唯一终点。

**状态必须分开：** 计算完成不等于原因成立；描述性发现不等于因果结论；加入报告不等于内容已确认；报告内容确认不等于策略批准。

**Demo 对应：** 3 张发现卡片、分析概览、门店汇总表、报告草稿及样例导出。报告默认包含 F01／F02，可从 F03 卡片加入第三项发现；已纳入的事实在本演示中不提供无痕删除。

**验收重点：** 每个重要判断都有依据入口；没有证据的项目明确显示“待验证”，不能用绿色勾选掩盖未知状态。

### 2.4 选中内容后继续对话，并保留业务上下文

**借鉴重点：** 用户不必复制一大段文字再解释“我指的是哪部分”。

**JuanerAI 改造：** 第一阶段只支持两种有边界的选择：数据结果中的行选择，以及报告中的文字选择。选中后出现“引用到对话”；可编审的解读段另有“局部改写”。

引用在输入框上方显示为上下文卡片。简单模式显示业务对象、时间范围和用途；专业模式补充数据快照、行标识、指标版本、报告版本或段落标识。引用不覆盖用户已经写下的草稿，可以单独移除。

**报告边界：** 数字和已确认事实只允许引用，不允许借由局部改写修改。经营解读先展示修改建议，再由用户“应用／放弃”。应用后报告升版，之前的内容确认失效，重新等待审阅。

**Demo 的具体限制：** 支持原生文字选择，但预置改写以“经营解读整段”为修改目标，选区用于保留上下文，不实现任意字符范围的精确补丁。界面明确展示这个范围，避免用户误以为只替换了选中的几个字。

**验收重点：** 引用能说明“来自哪里”；局部改写先提案，锁定数字与事实不变；没有模型时不假装回答任意业务问题。

### 2.5 关键过程可检查，技术详情不常驻

**借鉴重点：** 让系统的依据与行动可以检查，而不是把全部内部信息摆满首页。

**JuanerAI 改造：** 顶部常驻任务阶段和“待你确认／待你选择”入口。点击可以直接定位到确认卡片，而不是让用户在长对话中寻找。依据面板集中展示“证据／口径与资产／过程”。

| 内部能力 | 简单模式的业务表达 | 专业模式的附加信息 |
|---|---|---|
| Semantic Context Runtime | 分析对象、指标定义、范围与口径边界 | 合同／绑定标识、口径版本、数据快照 |
| Analysis IR / Analysis Core | 在检查什么问题，什么仍未验证 | Finding 标识、计划关联、方法或证据引用 |
| Harness / Execution Runtime | 已完成、待确认、失败或不可用 | 实际可取得的事件、执行与核验回执 |

阶段状态必须来自现有权威任务状态，不按聊天文案推断，不使用随机增长的百分比。没有真实回执时显示“未接入／未知”，不能为了页面完整填成“通过”。安装资产、任务绑定资产、实际调用资产、使用结果通过核验，是不同状态。

**Demo 对应：** 常驻“待你…”入口、五段示例阶段条、证据与边界、口径与示例资产、过程面板、简单／专业切换。所有执行／核验／资产绑定呈现均标为预置示例，不能作为真实调用证明。

**验收重点：** 切换信息深度不改变任务；风险、口径缺口、待确认事项在简单模式也不能消失。

### 2.6 视觉克制，但保持业务辨识度

**借鉴重点：** 降低界面噪声，同时保留用户判断所需的清晰层级。

**JuanerAI 改造：** 当前项目、分析对象、待确认事项、关键发现优先；技术细节和低频管理入口降级。采用浅色背景、清晰分隔、少量强调色和稳定的卡片样式，不用多色仪表盘或大面积装饰争夺注意力。

Demo 使用中性浅底、深色正文、克制的绿色强调和琥珀色待确认提示。此配色是本次提案，不是重新确定正式品牌规范。字母 J 为占位标识，不替代已确定的苍耳 Logo 与“持续做出更好的决策”理念。

**建议生产组件尺度：** PC 侧栏约 220–244 px；依据面板约 340–420 px，可在限定范围内调整；业务正文建议 13–14 px，辅助元信息可更紧凑。不要把截图中的每个像素当作硬性合同，最终应以现有设计系统、中文可读性和真实内容长度为准。

**验收重点：** 主体不横向溢出；面板不挤压主要内容至不可读；状态有文字而不只靠颜色；关闭、引用、发送等操作有明确名称与焦点反馈。

## 3. 页面与导航的初步安排

### 3.1 三种工作状态

| 状态 | 主区域 | 辅助区域 | 主要退出方式 |
|---|---|---|---|
| 对话状态 | 当前任务对话、发现卡片、待确认事项 | 默认不展开 | 打开依据或成果，不结束任务 |
| 辅助审阅状态 | 原对话保持存在 | 单一依据面板 | 关闭按钮、Escape；返回原对话 |
| 成果工作状态 | 分析概览／数据结果／报告编审 | 同一任务的紧凑助手 | 顶部“对话”或成果关闭按钮 |

首页的“本地资料”是轻量资料管理界面，不是新的分析流程。上传的正式处理逻辑继续由现有能力承接，不能因 Demo 有按钮就假定真实解析已经实现。

### 3.2 信息层级

- **全局稳定层：** 产品标识、项目、最近任务、资料入口、简单／专业切换。
- **当前任务层：** 任务名称、数据范围、阶段、待确认事项、对话／成果切换。
- **按需展开层：** 证据、口径、过程、数据选区、报告改写提案。

不把假设库、策略库、指标工作台、Model Pack、工具管理等全部平铺为首屏入口。本期只在当前任务需要检查上下文时展示相关信息；不新增相应后台子系统。

### 3.3 状态与操作必须保持一致

打开面板不触发新分析；关闭面板不取消任务；切换简单／专业不重新执行任务；改变报告表述不改变源结论；选择下一步排查方向不自动批准业务操作。

对于正式产品已有的暂停、恢复、人审或受限执行状态，首期只改善呈现并连接原入口。没有可用接口的动作保持“未接入”，不新造一套前端执行引擎。

## 4. 参考案例：销售下滑复盘

### 4.1 用户问题与演示数据

用户输入：

> 9 月销售为什么下降？先看门店和会员，不急着给促销建议。

本例全部为合成数据；与真实业务及用户上传文件无关。

| 门店 | 2026 年 8 月净销售额 / 元 | 2026 年 9 月净销售额 / 元 | 差额 / 元 |
|---|---:|---:|---:|
| 虹桥店 | 420,000 | 345,000 | -75,000 |
| 徐汇店 | 360,000 | 311,400 | -48,600 |
| 静安店 | 280,000 | 259,000 | -21,000 |
| 浦东店 | 220,000 | 211,000 | -9,000 |
| 合计 | 1,280,000 | 1,126,400 | -153,600 |

整体环比为 -12.0%。虹桥与徐汇合计下降 123,600 元，占下降额 80.5%。另一个会员维度中，老会员销售额由 800,000 元降至 650,000 元，减少 150,000 元，占整体下降额 97.7%。

这些数字为本文样例的算术关系，不代表实际分析已经执行。门店与会员是不同分解维度，贡献不能相加。

### 4.2 需要在 UI 中明确的业务边界

净销售额为实付减成功退款，取消订单不纳入；退款回溯至原订单支付月，示例快照截至 2026-10-10。比较的是自然月总额，尚未校正 8 月与 9 月天数、节假日和实际营业日差异。

“老会员销售额下降”不能直接改写为“复购率下降”。缺货、价格、促销等均只是可能解释，需要新增支持与反证。因此后续动作是选择排查方向，而不是直接批准打折。

### 4.3 推荐体验路径

1. 首页点击销售下滑案例，确认口径后载入预置结果。
2. 查看 F01／F02／F03，点击“查看证据”，切换口径与过程，再关闭面板。
3. 使用顶部“待你选择下一步”定位到排查卡；选择一个方向，观察“已记录、未执行”的边界。
4. 进入“成果 → 数据结果”，勾选虹桥与徐汇，将选区引用到同一对话。
5. 进入“报告编审”，选中解读文字或点击“试试局部精简”，发送后查看预置提案，应用或放弃。
6. 切换简单／专业，确认草稿、选择和报告版本没有因视图变化而被重置。

## 5. 前端落地方式：映射现有状态，不重造业务核心

以下是**前端展示模型建议**，不是要求后端立刻新增 API 或接受这些命名。前端实施前应先映射到当前已存在的任务、Finding、报告与回执结构。

| 展示对象 | 最小所需信息 | 缺失时的 UI 行为 |
|---|---|---|
| TaskView | 任务 ID、范围、阶段、待确认事项、版本 | 显示未知或未接入，不从对话猜测完成状态 |
| FindingView | 标识、摘要、数字、证据引用、结论状态、边界 | 证据入口显示缺口，不补造引用 |
| ContextView | 对象、指标口径、版本、范围与绑定信息 | 告知待确认／未绑定，不默认套用资产 |
| ArtifactView | 成果 ID、类型、版本、关联任务、内容确认状态 | 不把生成文件自动视为已确认报告 |
| SelectionRef | 来源、版本、选区、指标／对象范围、允许操作 | 绑定不完整时仅作为普通引用，不擅自执行 |
| ActivityView | 真实阶段与现有可获取回执的展示投影 | 显示无回执，不自造执行日志 |

选区展示模型示意：

```json
{
  "kind": "data_rows",
  "task_id": "DEMO-001",
  "dataset_ref": "demo-snapshot-01",
  "row_ids": ["S01", "S02"],
  "period": ["2026-08", "2026-09"],
  "metric_ref": "net_sales@demo-v0.1",
  "allowed_action": "quote_for_analysis",
  "provenance": "PRESET_MOCK"
}
```

Demo 中快照标识只是样例 ID，不是实际文件哈希。正式产品应复用真正的数据版本与引用系统，不能把上述演示字符串直接接入生产。

UI 局部状态只负责当前视图、面板开关、宽度、阅读位置、未发送草稿与选区。真实执行、核验通过、策略审批仍以既有后端事实为准。

## 6. 同一首期内的实施顺序

下列 UI-A／B／C 只是建议工作切片，不替代已批准 Change 编号或工程门禁。六项 UI 思路都属于本期目标，但真实接口依赖需要先核对。

| 顺序 | 工作切片 | 主要内容 | 完成标准 |
|---|---|---|---|
| UI-A | 工作台外壳与导航 | 对话起步、项目与上传入口、三种视图、简单／专业 | 任务、草稿和阅读上下文在视图切换中不丢失 |
| UI-B | 发现与依据展示 | Finding 卡、常驻待确认入口、证据／口径／过程 | 重要结论可追溯，状态与既有真实回执一致 |
| UI-C | 选区与局部编审 | 行／文字引用、单一主稿、锁定事实、审阅后应用 | 引用有范围，改写不越界，内容确认与策略批准分开 |

建议先评审 HTML 的操作逻辑，再审阅现有前端组件与 UI Contract；能够复用的组件优先复用。依赖缺失时交给 Controller 判定是否进入独立变更，不能借本次 UI 改造悄悄扩大后台范围。

## 7. 静态 Demo 的真实能力与限制

| 可以实际体验的本地交互 | 明确没有实现的能力 |
|---|---|
| 页面切换、项目入口、模式切换 | 真实项目数据库、账号或团队权限 |
| 选文件／拖放、文件元信息列表 | 读取或解析上传文件、数据清洗、百万行处理 |
| 口径确认、预置发现与依据展示 | LLM 分析、真实 IR、DuckDB／Python 主算复算 |
| 行选择、文字选择、引用上下文 | 任意数据区域的分析执行与完整电子表格编辑 |
| 预置改写的审阅、应用、放弃与本地升版 | 自由生成报告、精确字符补丁、真实报告存储 |
| 合成 CSV 与演示报告 Markdown 导出 | PPTX／PDF 生成、企业分发或策略执行 |

**技术形态：** 一个 HTML 文件，内嵌 CSS、原生 JavaScript 与 SVG 图标。无 npm、无框架、无 CDN、无远程字体或图片，不需要后端服务。无需共享或安装字体文件。

**状态保存：** 任务、草稿、选区和报告修改尝试写入当前标签页的 sessionStorage；浏览器不允许时退回内存。上传文件只记录名称与大小，元信息仅留在内存，不读取文件内容。关闭标签页、浏览器限制或刷新可能影响状态恢复，因此不能将本原型当作可靠存储工具。

**使用方式：** 下载 `JuanerAI_UI_Demo_v0.1.html`，用浏览器打开，从首页案例开始。右上角“演示说明”可以查看体验路径或清空本页状态。

**适用边界：** 窄屏回退只用于避免布局崩溃，不代表移动端产品已完成。本原型不能用来证明 JuanerAI 真实调用了资产、执行了分析或通过了任何业务核验。

### 8.1 首期正式前端的验收标准

| 编号 | 验收项 |

## 9. 提交给 Controller 的评审要点

先判断六项交互是否与现有 Xanthil 用户任务一致，再决定具体落入哪些页面和组件。需要优先确认的是三种视图的职责、待确认入口、Finding 与报告的引用关系，以及局部改写的权限边界。

通过产品评审后，再核对当前已批准 UI Contract、真实数据结构、已有执行状态与人审入口。采用增量方式实现，不为复刻 Demo 重写底座；不能仅凭页面显示“已核验”就认定能力已经接入。

本期成功标准是：**用户更容易启动分析、检查依据、继续追问与审阅成果，而严谨性、权限和执行边界没有被界面简化所削弱。**

## 1. 定位、版本及采用规则

JuanerAI 是从专业个人用户出发，逐步发展到团队和企业的
**Bottom-up Decision Intelligence System**。其产品主线是决策生命周期管理：
可信分析构成入口，让当时的依据、选择、行动与实际结果可追踪，再通过受治理的
改进影响下一次判断。记录、回访和审查的成本必须由实际价值证明值得承担。

初始用户仍是非技术业务／分析人员；会员复购诊断仍是首个冻结场景。
用户通过真实前端理解问题、依据、选择、预期、实际和下一步，不需操作源码、
JSON、IR 编译器、数据库或命令行。纯分析可止于有边界的洞察，不强迫行动。

### 1.1 为什么是 v2.0

沿用 v1.3 §1.3 的版本规则：兼容补充升次版本，非语义校正升补丁版本，
产品路线、目标用户、首切片、价值终点或核心验收边界的实质改变升主版本。
本次把结果回访和后续采用从主要后期价值推进到 Personal 阶段，改变个人重复价值
的终点及后续纵切顺序，因此升为 v2.0；不是机械跟随白皮书版本号。

白皮书仍是核心产品参考及商业化纲领；获批并完成整合的蓝图是产品开发执行指引。
白皮书更新须经用户通知、精确来源核对、逐项采用判断、用户批准版本化蓝图、
独立就绪审查及项目规则整合。任一步骤都不自动改写在研 Change。

### 1.2 本轮采用矩阵

“采用”是用户已批准纳入产品路线的内容，不表示已实现或获准立即实施。
“延期”保留目标和回看条件；“不适用”针对错误解释或当前纵切，不删除完整能力目标。

| 白皮书 v4.0 内容 | 蓝图处理 | 采用方式、延期点或禁止推导 |
|---|---|---|
| Bottom-up DI／Decision Lifecycle（§3–4） | 采用 | 用持续决策价值组织路线；可信分析质量仍是基础 |
| Case／Loop／Graph、System of Record、Lineage（§29–30） | 采用，分步交付 | Case 从问题开始；先持久记录及精确关系，再按真实查询需要扩展；不另建五套平台 |
| Personal → Team → Enterprise 及双轴（§25、27） | 采用 | Personal 对应 Desktop Free，Team 对应原 Workspace 产品；战略名称不自动改包名、接口、UI 或资产作用域 |
| Decision Record／Expected Outcome（§25.4、29） | 采用为下一纵切目标 | 在首切片基础上补正式选择与事前预期；不把“优先验证”改标成已作决定 |
| Future Actual／Outcome Evaluation（§31） | 采用到个人阶段 | 无 Model Pack 也可回访业务结果；行动、观察、校准、归因和决策质量分别判断 |
| Outcome 驱动学习与下一 Case 采用（§20.6–20.7） | 采用到个人阶段 | 评价 → 候选 → 正确 Owner／验证／版本 → 显式采用；发生与有效分开证明 |
| 五类 Core（§13–14） | 采用为逻辑职责映射 | 语义、分析、决策、学习、执行复用既有边界；不预冻结服务、路径、Schema、数据库或工程拆分 |
| 双库与 Graph（§12、30） | 采用语义；规模化能力延期 | 双库保留独立 Owner、准入和版本；在个人跨 Case 查询评审及 Team 准备时复核扩展必要性 |
| Analysis IR／Semantic Context（§11、16） | 保留并明确位置 | IR 约束一轮分析执行与验证，Case 组织业务全过程；不增设通用 Decision IR，不把 IR 当独占壁垒 |
| Domain Pack／Model Pack（§18） | 保留并按消费需要扩展 | 领域决策方法可扩展；模型质量和业务决策效果各有验收；旧 Desktop 后启动 Model Pack 的顺序仍作废 |
| OSM／PIM、三模式、DAME、六条主线＋两贯穿能力 | 全部保留 | 按 §4 覆盖与回看，不成为并行造模块清单；普通 PIM 不要求 Objective／Gap |
| Report Studio／Deep Research | 保留，按需求选择 | 分别表达已有分析／决策依据、补充外部证据，不接管业务事实或最终决定 |
| 竞争与专业评估（§24、28） | 采用 | 领域深度、结果历史和学习是待验证优势；不以功能、架构或节点数量宣称优越性 |
| 企业 Graph／SSO／多租户／跨客户学习／自动行动 | 近期延期或无默认权限 | Team／企业试点或单项自动化提案时再评估；数据共享、训练、执行分别授权 |

六条主线的删减、场景更换或价值终点变更仍需用户明确决定；不能以本蓝图的
“先做最小闭环”解释为取消其余已批准目标。

## 2. 产品语义与共同边界

| 概念 | 产品责任 | 不等于 |
|---|---|---|
| Decision Case | 从问题开始保存身份、修订、责任、范围、依据及过程引用；内容逐步补齐 | 聊天标题、末尾报告包装、单次 Run |
| Decision Loop | Case 从问题到结果评价，再影响后续 Case 的价值过程 | 每个 Case 必须采取行动，或每次分析已闭环 |
| Decision Record／System of Record | 保存当时可见依据、备选、选择／不行动／暂缓及理由、责任和适用预期 | 正确答案库、Memory、行动批准 |
| Decision Graph／Lineage | 带来源、版本、时间及作用域的 Case／证据／资产／选择／结果关系 | 新事实真源、必须采用图数据库、同源材料多次独立佐证 |
| Expected Outcome | 观察前记录的预期、基准、窗口、护栏和评价安排 | 目标愿望、保证收益、事后补写的预测 |
| Future Actual | 在约定对象与窗口取得、有来源和质量说明的实际观察 | 预测、目标、LLM 推测、行动完成回执 |
| Outcome Evaluation | 区分执行符合性、实际观察、预期校准、策略归因和当时决策质量 | 指标上涨就证明策略有效；坏结果就证明当时决定不合理 |
| Recall／Reuse／Learning | 找回历史／检查适用性后复用／依据结果形成改进并用于后续任务 | 三者可以互换，或保存摘要即完成学习 |

分析完成、作出决定、行动完成、结果评价完成分别表达；改进候选、批准版本、
实际采用和效果证据也分别表达。失败、不行动、暂缓、缺数及尚未成熟的结果均保留，
不补造成功，也不从评价样本中静默排除。旧决定和预期保持当时版本；新认识追加修订。
这些是产品语义，不是新增状态枚举或持久化 Schema。

Data 和 Ontology 的基础权威、Hypothesis／Strategy 的资产权威、Knowledge／Memory
的背景能力沿用[资产与模型架构](../../architecture/asset-and-model-capability-architecture.md)。
Case 记录“当时依据与责任”，不夺取外部交易事实、OSM 对象或资产 Owner 的权威。
Graph 的查询与摘要同样受源权限约束；失去授权不能借旧摘要继续暴露敏感内容。

阶段评审在现有规划中逐行记录“已验收行为及证据、未达目标、下一候选、依赖、回看点”。

## 5. 视图二：产品形态、成熟度与阶段路线

### 6.2 下一候选：决策记录与事前预期

**完整用户任务：** 重开已验收能力所支持的会员复购 Case，检查候选及当时证据，
记录自己的选择／不行动／暂缓、理由与责任；对适用决定保存事前预期和观察安排，
之后重开仍能回答“当时为什么这样选，准备怎样检查”。

- 复用已有 Case、候选、来源、版本、保存／重开及报告入口，不再开发一套历史系统。
- 产品应表达当时证据及备选、选择与理由、决策者／确认时点，和适用的基准、指标、
  对象、预期／不确定性、观察窗口、护栏、结果来源与评价安排。
- Draft、用户确认的记录、后续修订可区分；取消未确认编辑不会生成已确认决定。
  改选或调整预期保留原依据；不能在实际结果到达后倒写原预期。
- 不行动、暂缓和信息不足是合法结果；纯分析不被强迫填写虚假行动或效果预期。
- UI 通过已接受的 PX-004/006 工作台增量呈现“我的选择／预期／回访安排”，
  不重做产品壳。已有 Preview 功能不因此被激活。
- 验收至少覆盖选择／不行动／暂缓、未确认退出、修订与历史读回、缺少必要依据时
  不冒充已确认、以及零外部行动副作用。用户必须能在正常 UI 中辨认这些事实。

**当前边界：** 只补记录及观察准备，不实施 CRM／营销动作、自动通知、自动审批、
新的模型调用或效果判断。精确交互、字段必填条件与可见失败须在 §7 产品输入中
确认后才交工程，不由此目标描述直接启动 Spec。

### 6.3 随后：结果回访与复盘

**完整用户任务：** 回到前次决定，说明获准的线下行动实际发生了什么，导入或记录
有来源的实际观察，对照原预期和护栏，形成有边界的复盘及后续建议。

- 首期可人工记录已有线下行动及导入结果；这是记录机制，不是许可执行真实行动。
  人工声明必须显示来源／可信等级，不能冒充独立系统回执。
- 决定记录、行动批准、实际执行与回执、Future Actual、评价分别保存和呈现。
  没有独立证据时，只能报告实际具备的证据等级。
- 观察须核对对象、指标口径、时间窗口、数据来源、覆盖／缺失和成熟度。
  未执行、未到期、失访、缺数、口径漂移与护栏失败保持可见，不能默认成功。
- 复用新数据修订、计算、来源及报告基础；补足 Expected／Actual 对应关系和资格
  检查。原 v1.3 的周期重跑／版本比较候选转为这里可复用的增量，不是独立默认首选。
- 区分执行偏差、实际观察、预期校准、策略归因和决策质量。无适用对照／评价设计时
  明确无法归因；结果改善不等于策略增量。迟到数据／更正追加观察或评价修订。
- 验收包括合法观察与复算、尚未到期／缺数／不匹配拒绝、回执与效果不混淆、
  历史预期和原评价可读、以及不因复盘自动启动下一行动。

**当前边界：** 不要求自动触达、全量 OSM、企业连接器或新模型训练。当前冻结方法
不被假定足以评价任何策略效果；场景需要新方法时，由明确需求单独确定范围。
真实用户、业务数据、行动和结果访问仍需分别获得对应权限。

### 6.4 再后：改进与下一 Case 显式采用

**完整用户任务：** 从一次有来源的结果评价提出一个具体改进，交正确 Owner 验证与
决定，形成可识别的新版本；后续适用 Case 明确采用它，并比较分析或选择的变化。

- 先选择一种当前确有需要的改进类型，例如假设适用条件、反证要求或方法规则；
  其类型和 Owner 在该纵切产品输入中明确，不一次实现所有资产后端。
- 复用 Owner、Context Commit／Teach 的语义：候选可被拒绝，验证不足不发布；
  已批准版本不自动采用，推荐也不改变旧 Case。
- 后续 Case 保留来源评价、批准版本、适用性、采用／未采用原因及真实变化。
  旧 Case 按原版本可读；同一 Case 的一次重跑不能冒充跨 Case 采用。
- “学习发生”需要可追踪采用及分析／选择改变；“学习有效”还需在独立留出或后续
  可比任务中继续检验质量／效果。结果未成熟时只声明已发生，不声明有效。
- 验收覆盖正确 Owner、候选拒绝、未批准／不适用版本拒绝、显式采用、旧历史不变，
  以及不能把未来结果泄漏进原决定或独立评价材料。

**当前边界：** 不自动训练、更新全部假设可信度、改变 Ontology、发布 Pack 或跨客户
共享。可先形成最小来源关系和查询，完整 Graph 服务不是该用户任务的前提。

### 6.5 Decision Loop MVP 的完成判断

在一个明确角色和可观察结果的场景中，共同验证：

1. 真实问题形成具有责任、范围和版本的 Case；
2. 分析依据来自真实受控计算、验证和可追踪证据；
3. 证据支持可审查 Options，或明确不足以建议；
4. 决定与事前预期接续适用行动证据、合格实际观察和有边界评价；
5. 结果产生经治理的改进，下一 Case 显式采用并检验变化及后续效果。

只完成前几项仍可有独立用户价值，但不宣称整个 MVP 完成。尚无后续结果时，
可以验收学习接续的软件行为，不可宣称真实学习效果。纯分析任务和适用决策闭环
分别统计。合成 UI／Demo 只能证明限定流程，不能补造真实经营闭环。

### 9.2 IR 仍是分析执行与验证合同

```text
Case 问题／适用 OSM Gap → 草拟 Analysis Contract
→ 获准 Context／Binding／能力版本 → 确认 Contract／Analysis IR
→ 物化查询／代码／模型／研究计划 → 受控执行与独立验证
→ Evidence／有限判断 → Options／用户决定 → 独立行动及结果／学习接续
```

IR 表达本轮分析怎么执行、验证和交付，执行必须真正消费它；不是装饰性 JSON、
单独生成 SQL、CPU 机器语言或整个业务生命周期。Case 不代替 IR，IR 不批准行动。
历史依据绑定当时数据／语义／方法／模型身份，不用 latest 改写过去。
缺匹配输入或环境时说明不能精确重放，不保证相同 LLM 输出或未获准的通用恢复。

保留已集成的 TypeScript Core／Application／Ports／Profiles、CLI/local-analysis、

contract-enabler。当前可复用的准确实现及测试映射由工程接收核对，不由蓝图重建。
参考[复用基线](../../governance/xanthil-first-slice-reuse-baseline.md)与
[复杂度控制](../../governance/change-complexity-control.md)，历史文件名不是当前代码事实。

Desktop 的 Electron／React／TypeScript、受控 Main／Renderer、操作状态与不可变
产物等是保留的首切片方向；其实现／验收以该 Change 证据为准，不写成已经完成。
Pi 保持既有有效 Adapter；第二 Runtime 遵循
[ADR 0003](../../adr/0003-business-runtime-port-strategy.md)，不因五类 Core 引入通用
Runtime、自动 fallback 或热切换。新数据源、方法、Pack、模型和基础设施必须服务

本蓝图不宣称领先同类产品。对照对象是用户实际使用的人工、表格、BI、文档或

| 团队和组织学习 | 共享语义、复核、作用域内 Graph 与治理 | Team／企业：多人复用、决策周期和维护成本、付费意愿及场景收益；不靠锁定导出或默认汇集客户数据 |

v1.3 的七项竞争假设均有承接：编译、调查、澄清、领域能力和可用／可控体验继续
作为入口；经验积累与决策到结果学习在 Personal 阶段提前验证。IR、Memory、图谱或
模型供应方本身不被称为不可复制的护城河；长期优势仍取决于合法、高质量、可比较
且被后续任务采用的领域方法和结果证据。

评价分层：技术产品可用、个人任务价值、决策记录、合格结果回收、学习接续、
学习有效性、留存、团队及企业价值不能互相替代。WVAT 保留为入口效率指标。
每项研究在开始前确定授权样本、分母、窗口、去重、失访／撤销、评价者、阈值及
失败／未知处理；本文不编造统一成功率、观察天数或收入目标。

真实效果主张必须有适用设计；没有因果证据也可改进数据／观察方案或提出假设，
但不宣称策略有效。未来实际不能泄漏到当时决策或独立验收材料。
指标可本地计算；联网遥测、分享、真实用户研究和跨客户训练各自授权，关闭遥测
不影响个人核心功能。若记录／回访负担超过收益，先收窄交互与适用场景再评估。

## 4. U1 must be real; persistence must survive progression

U1's end-to-end closure is native Project selection → real store open/create →
professional Session creation → three-directory publication plus SQLite commit →
case-fields save → list/open/projection → close and reopen the same case in the
same production app. It includes duplicate-command handling, collision, failed
publication, COMMIT unknown/receipt readback, real native SQLite crash recovery,
identity, containment and Main isolation. These are U1 prerequisites, not deferred
hardening. It must not require constructing Analysis/Run/Assistance Adapters.

The Store's internal U1 subset must support the actual path above, including
receipt/validation/projection reads; Spec chooses the exact minimal method set
from the existing contract, with any necessary narrow private translations.
There is no obligation to export future mutations merely to satisfy the final
interface shape. Full schema and projection shape do not require creating future
business records or implementing their write lifecycle.

At the U1 completion checkpoint, the seven active public operations are
`selectProject`, `listSessions`, `openSession`, `createSession`,
`saveForm(case_fields)`, `readProjection`, and `waitForProjection`. Earlier U1
micro-loops may activate an exact subset as they become real; the unit is not
complete until all seven and their required failure paths work. The internal
closure uses the same-named Application calls (`selectProject` enters Profile
and Application `openProject`) and Store's existing open/list/create/save/read/
wait operations plus required integrity/receipt handling; a receipt helper need
not become a new public Port. Main's only U1 native chooser is Project selection.

U1-supported stored state is an initialized Project, zero or more professional
Sessions each at its first Draft revision, editable case fields and row versions,
the original `ok|integrity_blocked` integrity marker, and receipts for
`initialize_project`, `create_session`, `save_form` of case fields or
`mark_integrity_blocked`. All source/current/previous authority references are
null and all later-capability tables are empty. The full sixteen-table schema
still exists. Empty future projection arrays are valid only after that fact was
read, not a substitute for reading. A later-record/state/receipt/reference causes
the supported-build refusal below, not a destructive attempt to make it U1 data.

For intermediate developer builds, open only Projects whose committed records
are supported by that build's admitted capabilities. The storage Adapter applies
the original header/schema/integrity preflight, then read-only checks for records,
current references, form kinds and lifecycle states requiring an absent behavior.
Unknown or unsupported future rows must not be silently omitted, treated as empty
arrays, repaired, or marked corrupt. Before any business-write connection or
semantic reconciliation, refuse the entire Project with existing public
`FORBIDDEN`: use the later/full build, original data preserved. Spec may define the
minimum closed internal admission result/error needed to carry that refusal
through Adapter → Profile/Application → Main; it is not a new persisted or public
error vocabulary, generic query Port or runtime phase selector.

The existing narrowly authorized native SQLite hot-journal recovery is unchanged
and may occur before schema/record inspection; its physical rollback writes must
be distinguished from the prohibited business writes on refusal. Never claim
zero physical effects for that branch. Foreign/schema/WAL/containment rejection
keeps the original zero-write rule. U1 Session crash/reopen cannot be replaced by
a blanket rejection of every journal. A later build must open earlier supported
Projects without migration, default filling, new receipts or altered identities
merely because the build advanced. It then applies only the original valid
reconciliation/integrity rules. Downgrading to an earlier developer build need
not execute later capabilities: truthful refusal, not destructive downgrade.

For each tuple, Spec must specify which existing table/record/state variants are
supported and their read/write dependencies. Exact predicates, method subsets
and test commands are Spec outputs; the admission/rejection meaning above is not
left to Test or Worker. No custom journal parser, database scanner beyond the
existing selected Project, backup service, new state field or migration is added.

## R216 — bounded unpublished evidence-commit clarification

This is an additive clarification of existing `REQ-M2-005 / AC-M2-005-03` and Foundation `REQ-DTF-005 / AC-DTF-005-07`; it creates no Requirement or Acceptance Criterion.

- `production.mjs` SHALL expose the closed local factory `createUnpublishedLedgerEvidenceCommitBuilder({repositoryRoot,stateRoot,gitExecutable,runtime_uid,runtime_gid}) -> Object.freeze({construct})`. Its only call is `construct({prepared_receipt:LedgerPreparedAppendReceiptV1,prepared_bytes:Uint8Array})`. Constructor and request objects are exact closed data. Before any await/effect it snapshots the fourteen-field receipt and copies the bytes; later caller mutation is irrelevant. Roots, fixed Git and actual uid/gid are trusted local bindings. The snapshot fixes the Evidence ref, null-or-40-hex predecessor, derived `ledger/<change_id>.jsonl` path, exact new bytes/hash/length, prior prefix/hash/length, and exact final canonical JSON+LF record whose Change/event/hash/sequence/idempotency identity equals the receipt. Null/path-absent predecessors require empty prefix and sequence one; an existing target's physical old blob must equal the prefix and its appended sequence must follow the prior canonical last record. Invalid constructor input throws `INPUT_INVALID`; an invalid or unbound snapshot throws `INVALID_RECEIPT` before effects. This does not duplicate Core event business validation.
- An `OK` value is exactly `{publication_status:'UNPUBLISHED',parent_tip,commit_sha,tree_sha,authoritative_path,ledger_blob_sha,ledger_bytes_sha256,ledger_byte_length,changed_paths:[authoritative_path],preserved_entries_sha256_before,preserved_entries_sha256_after}` plus the existing canonical `receipt_sha256`. It proves only local Git objects and bytes. It is not the existing `LedgerEvidenceCommitReceiptV1`, contains no remote or ACK/linearization claim, and creates no authority until the unchanged protected writer publishes and the existing exact remote readback linearizes.
- The builder SHALL use only fixed local work/index paths derived below the admitted `stateRoot`, fixed Git commands/environment/cwd, and the existing process/atomic-write implementations. It SHALL physically prove predecessor commit/tree and old target blob/prefix, prepared file bytes, new blob/tree target, all non-target recursive entries, and final commit tree/parent/message. Null predecessor means an empty before view and zero-parent commit. It reuses the existing object-reader completion/header rules. `read-tree`/`update-index` require empty stdout; OID-producing commands require one nonzero lowercase 40-hex plus LF; `cat-file -t` recognizes commit/tree/blob/tag plus LF but a success assertion accepts only its expected commit/tree/blob type; target `ls-tree` is absent or one exact regular-blob record. The final commit has one exact tree, zero or one exact expected parent, valid single author/committer headers, and exact message body. No output is trimmed into validity.
- Canonical preserved-entry bytes are the unsigned-raw-path-sorted concatenation of validated NUL-terminated recursive leaf records `mode SP type SP oid TAB path NUL` from `ls-tree -r -z --full-tree`, excluding only the exact authoritative-path record. Raw path bytes are not decoded/re-encoded; allowed pairs are exactly `100644 blob`, `100755 blob`, `120000 blob`, and `160000 commit`. A predecessor exact target is allowed only as `100644 blob`; an ancestor, descendant, duplicate, or other-mode/type target collision rejects. After construction there is exactly one `100644 blob` target whose blob bytes equal the prepared bytes. Success requires both preserved byte sequences themselves and their SHA-256 values to be equal.
- Error priority is input rejection, then process availability, then proven object disagreement. Start/throw/nonzero/signal/stderr/timeout/overflow, filesystem failure, missing object, malformed control-command empty/OID output, or `cat-file -t` output outside exact `commit\n|tree\n|blob\n|tag\n` returns only `{kind:'UNAVAILABLE',reason:'PROCESS_FAILED',partial_receipt:null}`. Any recognized but non-expected type, including `tag\n`, or—after exact completion/identity—malformed physical commit/tree-entry bytes or parent/tree/path/blob/byte/message disagreement, returns only `{kind:'CONFLICT',reason:'READBACK_MISMATCH',observed_identity:null|git_sha}`. Neither permits protected transport. Derived working files/index artifacts and unreferenced objects may remain; there is no local-ref update, cleanup, durability or rollback promise.
- The original private Ledger writer and isolated Test SHALL consume this same production body. Only while `prepared.publication` is null does the writer call it with actual retained snapshots. Non-OK remains uncached and stops that call before transport; a later caller retry may construct again under the same null condition, without builder-internal retry. One OK is cached, and only then every same-prepared-identity call reuses it unchanged. A new prepared append resets that private slot. The builder has no cache/retry/recovery. The writer retains the existing four Ledger signatures, credentials, protected push/readback and complete `LedgerEvidenceCommitReceiptV1`, and copies both proven preserved-entry hashes into that receipt. No full Ledger factory, credential, remote URL, arbitrary ref/path/argv/env, callback, runner/parser/result injection, test runtime, State/lock/retry/recovery, or persistent schema is added.
- Test/implementation activation is strictly two-stage: absent export causal RED; `TDD_READY-ENTRY` for mechanical extraction/delegation that preserves and exposes the old deficient body and temporary internal `{tree,commit}` result; source-preservation plus independent physical readback of one healthy mechanical publication; then a real index/filesystem failure on that same body whose returned/cached publication is independently proved physically bad, not merely the wrong return shape; then a separate TDD_READY for the minimum correction. The intermediate is intentionally nonconforming and non-releaseable, has no legacy mode, and cannot count as F1 evidence. If no approved real failure can expose the old physical defect, the Change blocks before implementation.
- Formal entry/behavior/GREEN evidence retains pre/post inventory, independent readback, exact source/Test identity, complete inner/outer logs and session/exit/freeze references. Retirement may remove only Test-owned non-formal scratch execution resources; it never deletes cited formal evidence and creates no cleanup Gate.
- F2 receives no normative change and remains the existing Core/State/strict Port behavior: exact eleven-field `StatusDiagnosticsV1`, separately exact sixteen-field `LocalPauseDiagnosticV1` only when genuinely persisted, two payload oracles, and all six crash-window meanings/Change-B/forbidden-effect duties. Test rebinds their old faulty request/outcome/call observations to the compliant strict read chain; the old short request and same-dependency-exactly-twice coupling are not retained. Only a genuinely persisted diagnostic permits `pointer_status:'INVALID'`; with no safe diagnostic, status returns the existing exact `CoordinatorErrorV1` `{schema_version:'1.0',operation:'status',outcome:'REJECTED',error_code:'WIP_AUTHORITY_INVALID',change_id:null|string}`, not a STATUS payload. F3 stays withdrawn. Existing A2/S09 and A3 evidence dispositions are unchanged.

## ADDED Requirements

### REQ-M2-001 — Fixed Signed Validation Definitions and Regression Binding

The Coordinator SHALL preserve the signed validation commands and execute exactly the approved purpose-bound definitions without index inference or defaults.

- **AC-M2-001-01 — Six-field admission:** DISPATCH `payload.validations` SHALL contain exactly three plain closed six-field definitions `{id,argv,cwd,environment,timeout_ms,subject}`. There SHALL be exactly one each of `regression-affected-suite`, `regression-test-asset-retirement`, and `final-validation-candidate`; unknown, missing, duplicate, or cross-subject definitions SHALL reject before pointer, State, Ledger, Git, validation, Agent, PR, or Handoff effect.
- **AC-M2-001-02 — Fixed purpose map:** `regression-affected-suite` SHALL map only to `REGRESSION / AFFECTED_SUITE / WORKTREE`; `regression-test-asset-retirement` only to `REGRESSION / TEST_ASSET_RETIREMENT / WORKTREE`; and `final-validation-candidate` only to `FINAL_VALIDATION / CANDIDATE / CANDIDATE`. Execution order SHALL be affected Regression, Test Asset Retirement, and only after Candidate commit the final validation. Signed array position SHALL confer no meaning.
- **AC-M2-001-03 — Eight-field derivation:** Each admitted signed definition SHALL derive one exact eight-field execution definition `{id,validation_kind,validation_scope,subject,argv,cwd,environment,timeout_ms}` by adding only the fixed kind and scope. `argv`, `cwd`, `environment`, `timeout_ms`, and `subject` SHALL remain byte/value identical. `command_definition_sha256` SHALL hash canonical JSON of the eight-field execution definition and SHALL NOT be represented as the signed six-field object hash.
- **AC-M2-001-04 — Post-Worker subject:** The two Regression executions SHALL receive the same exact `WorktreeSubjectV1` assembled from signed repository/worktree/scope plus fresh Git branch, Head, common-dir, empty-index, and content observation. Initial execution Head SHALL be the approved baseline; the one repair execution Head SHALL be the preceding Candidate. Role assertions or the worktree's old creation-time clean result SHALL NOT supply subject facts.
- **AC-M2-001-05 — Two-receipt gate:** Both twenty-four-field Regression receipts SHALL be complete `COMPLETED/PASS/null`, have the fixed IDs/kind/scopes, bind the same Head/scope/worktree snapshot, and be durably read back from the current Change Ledger before STAGE. Either failure, receipt mismatch, Ledger mismatch, or content drift SHALL authorize no STAGE or Candidate.

### REQ-M2-002 — K1 Exact Dirty-tree to Candidate Identity Chain

K1 SHALL turn one actual allowed post-Worker dirty tree into one exact Candidate without staging scope patterns, losing path bytes, or accepting content that Regression did not validate.

- **AC-M2-002-01 — Legitimate dirty worktree:** Candidate preparation SHALL require the exact repository, Worktree, branch, common-dir, expected Head and empty index. The worktree SHALL contain at least one actual difference and every difference SHALL be within allowed scope and outside forbidden scope. An empty Worker diff, staged index, conflict/unmerged entry, ignored entry, unsupported status, scope escape, or identity mismatch SHALL stop before validation or STAGE as applicable.
- **AC-M2-002-02 — Lossless observed paths:** Fresh `inspectWorktree` evidence SHALL enumerate the complete actual added, modified, deleted, type-changed, and untracked path set from NUL-delimited machine output. Paths SHALL be non-empty canonical repository-relative primitive strings with exact UTF-8 round-trip, sorted uniquely by raw UTF-8 bytes. Spaces, Unicode, and pathspec-like ASCII characters are data. Invalid UTF-8, NUL, absolute/dot/dot-dot/backslash paths, rename/copy, duplicates, conflict/unmerged, ignored, or unsupported status SHALL fail closed rather than be normalized or omitted.
- **AC-M2-002-03 — Scope is not a stage list:** Signed allowed/forbidden rules SHALL only filter the observed actual paths. `stageExact` SHALL receive that sorted actual path list and SHALL use literal, NUL-safe path transport; glob/pathspec expansion, broad add, repository-root staging, and unrelated paths SHALL be unavailable.
- **AC-M2-002-04 — Content drift fence:** The second Regression post-snapshot is the expected pre-stage `worktree_snapshot_sha256`. The stage operation SHALL re-observe the same Worktree subject, require that snapshot to equal both Regression receipt snapshots, retain the exact pre-stage entry identities while staging, and prove after staging that indexed content equals those identities with no unstaged, untracked, or ignored remainder. Before Candidate creation, the existing four-key `readCommit` SHALL prove the expected parent's exact SHA/tree/branch from its existing `canonical_root` cwd. Only a successful physical commit-byte read that contains zero parent headers may express a historical root as `parent:null`; failed, absent, malformed, graph-derived, all-zero-parent, self-parent, or uncertain reads SHALL NOT become root success. A nonroot read retains its accurate nonzero full 40-hex parent distinct from the commit SHA. Drift observed before the explicit commit-object operation SHALL reject before a branch move. The actual commit SHALL select the already verified tree explicitly rather than reread content from the mutable index; later index/worktree/ref drift may therefore be detected only by post-commit readback, where it SHALL stop without publication but SHALL NOT alter the selected commit tree. No repeated observation or mutex SHALL be treated as exclusion of an external writer, and no new content-hash protocol, persistent transaction, lock, retry, rollback, read method, request field, result key, or parents collection is added.
- **AC-M2-002-05 — Staged readback:** `stageExact` and `readStaged` SHALL return the complete same sorted staged path list, its canonical SHA-256, and the same full index tree. The tree SHALL differ from the expected parent tree, and no unstaged, untracked, or ignored remainder may exist. A path-set-only match without content/tree equality SHALL NOT pass.
- **AC-M2-002-06 — Candidate commit and readback:** STAGE, staged readback, Candidate commit, and complete Candidate/event/State readback SHALL occur in one public `run` with no intermediate State publication or return. Candidate creation SHALL use `commit-tree <stage-verified-tree> -p <fresh-parent>` with an accurate non-null, nonzero full 40-hex parent distinct from the Candidate SHA and the exact idempotency-bound message, followed by old-parent compare-and-swap `update-ref`; an ordinary index-reading commit is forbidden. The physical Candidate commit SHALL have exactly one parent. Candidate success, `CANDIDATE_COMMITTED`, Candidate State, convergence, and final readback SHALL reject `parent:null`, all-zero, self, missing, multiple, or wrong parents and prove that one parent equals the exact expected parent, together with exact SHA, tree, message identity, branch, Worktree Head, common-dir, empty index, and fully clean status. A synchronized index/worktree replacement before staged readback rejects; one after that readback cannot change commit content and SHALL be exposed by the final readback as a post-commit identity stop. A stop before `commit-tree`, after an unreachable commit object but before ref CAS, and after successful ref CAS have the distinct authority effects in Design. If the process stops after physical stage but before K1 publication, persisted STAGE does not contain the independent verified tree; restart SHALL enter existing `CANDIDATE_COMMIT_AMBIGUOUS / MANUAL_CONTROLLER_STOP` without deriving expected content from observed Head/tree/diff/trailer, restaging, committing, cleaning, or publishing. Only the still-running invocation retaining the independent expected identity may use Candidate readback convergence. A zero-content Candidate or parent, tree, branch, or Head mismatch stops under the existing disposition.
- **AC-M2-002-07 — K1 completion:** K1 completes only after the complete `CANDIDATE_COMMITTED` event is remotely read back and State persists the exact Candidate with empty `validation_refs`, null `validator_head`, and `frozen:false` at `DELIVERING / FINAL_VALIDATION`. K1 does not prove K2, publication, or external readiness.

### REQ-M2-003 — Closed Candidate Final Validation Branch

The existing production `validation.execute` SHALL retain the accepted WORKTREE branch and add only one closed Candidate branch.

- **AC-M2-003-01 — Closed request union:** `validation.execute` SHALL accept exactly `{definition,subject}` where the pair is either the accepted WORKTREE/REGRESSION branch or the new `CANDIDATE/FINAL_VALIDATION` branch. The WVEB statement that Candidate input is invalid remains normative inside the WORKTREE branch: a Candidate paired with either Regression definition, or a Worktree paired with `final-validation-candidate`, is cross-subject `INPUT_INVALID` with no receipt or child. No arbitrary subject or validation registry is added.
- **AC-M2-003-02 — Candidate subject:** The Candidate branch SHALL bind the current Candidate SHA/tree, repository root, Worktree root, branch, common Git dir, and signed scope. Before and after the one child it SHALL prove exact Head/tree/branch/common-dir, empty index, fully clean worktree, allowed execution cwd, and unchanged Candidate identity.
- **AC-M2-003-03 — Twenty-four-field branch table:** Candidate execution SHALL return the same exact twenty-four fields as WVEB. `subject_kind` SHALL be `CANDIDATE`; `subject_sha == head_sha == candidate_sha`; `candidate_tree` SHALL be the exact non-null tree; `validator_head` and `worktree_snapshot_sha256` SHALL be null; `scope_sha256` SHALL be non-null. `execution_cwd` alone may be null on pre-execution `START_FAILED/null/SUBJECT_MISMATCH`. Other request-derived identity and empty-output hashes SHALL remain populated. The seven existing status/verdict/failure tuples and receipt-hash algorithms SHALL be unchanged.
- **AC-M2-003-04 — Process and mismatch order:** Candidate execution SHALL preserve WVEB's descriptor-first admission, empty parent environment, one child, timeout/signal ordering, raw stdout/stderr hashing, and mandatory post-observation. A pre-observation mismatch starts no child; a post-observation mismatch has precedence as `INTERRUPTED/null/SUBJECT_MISMATCH`. There is no retry, recovery, second child, rollback, or configurable termination policy.
- **AC-M2-003-05 — Candidate-only references:** Only after the complete Final Validation PASS receipt and its exact `VALIDATION_RESULT` event are remotely read back may State add the Final Validation reference to `candidate.validation_refs` and request a fresh Validator. Regression receipts bound to a pre-Candidate Head SHALL NOT enter Candidate-only refs.

### REQ-M2-004 — Validator Artifact, Result, and One Causal Repair

Validator outcome and repair eligibility SHALL come only from a closed, hash-bound Validator artifact for the exact Candidate.

- **AC-M2-004-01 — Closed artifact:** The Validator artifact SHALL use `ValidatorArtifactV1` from Design, including exact `change_id`, `candidate_sha`, `validator_head`, `verdict`, findings, risks, unverified items, and open questions. It SHALL be canonical, satisfy the signed `output_schema_sha256`, and match the full artifact SHA-256. Missing, extra, ambiguous, unclassifiable, conflicting, or noncanonical content SHALL not advance.
- **AC-M2-004-02 — Host courier and shared launcher:** Only the Validator RESULT settlement adds `validator_artifact`. The host SHALL read and hash the actual artifact, verify its bounded shape against the signed output schema, and forward the parsed artifact unchanged. It SHALL NOT derive Head from the request, write PASS/FAIL, classify findings, clear arrays, or expose a general artifact-reading Gateway. Ordinary non-Validator RESULT and all STARTED/START_FAILED/INTERRUPTED contracts remain unchanged; only the exact CCR002 repair Test/Worker RESULT extensions in Design 7.2 are added. Every ordinary and repair Agent launch SHALL use the same purpose-bound `createHostAgentLauncher({resultRoot,prepareResultRoot})` implementation in the existing `host-loop.mjs`. The closed construction object SHALL accept only an absolute normalized `resultRoot` path and a no-result directory-preparation function; each closed call SHALL accept only `{action,route}` and require the route artifact path to equal `<resultRoot>/<correlation_id>.json` with a single safe correlation path segment. The preparation function SHALL receive only `{resultRoot}`, SHALL complete before spawn, SHALL return only `undefined`, and SHALL NOT provide route, identity, parser, artifact, receipt, verdict, proof, process, filesystem, clock, timer, timeout, or retry behavior. Production SHALL construct it with the fixed `AGENT_RESULT_ROOT` and existing mkdir/chown/chmod behavior; Test MAY construct it with a real current-user temporary root and real local preparation. After preparation and before spawn, the expected output path SHALL be either absent with an exact physical `resultRoot` parent or an existing regular non-symlink whose realpath and physical parent are exact; a known symlink, non-regular entry, escape, or read failure SHALL start no child. The same physical path/regular-file checks SHALL repeat after close before parse, followed by the existing exact-path Host Loop re-read/hash agreement. Invalid factory construction SHALL throw synchronous `INPUT_INVALID` before an action exists and SHALL produce no settlement. Once a valid factory exists, invalid call/path, unreadable input/schema, preparation or pre-spawn output-identity failure, synchronous spawn failure, or invalid PID before STARTED SHALL map to existing `START_FAILED/SPAWN_REJECTED`. After STARTED, child error or artifact physical-path/read/hash/parser/inventory/Host-Loop-re-read failure SHALL map to existing `INTERRUPTED/RESULT_UNREADABLE`. These checks add no lock or absolute exclusion of an external writer. For an ordinary launch, a fired action deadline SHALL force existing `INTERRUPTED/AGENT_EXITED` after the real close even if the fixture handles SIGTERM and closes with `code:0,signal:null`; no valid artifact may then produce RESULT/PASS. An ordinary non-deadline signal close retains `INTERRUPTED/AGENT_EXITED`. The repair-only Design 7.4 branch has the more specific rule that any signal, fired deadline, wrong exit/TAP, or later proof failure after STARTED is `INTERRUPTED/RESULT_UNREADABLE`. No fallback to current-user production launch is permitted.
- **AC-M2-004-03 — Coordinator validation:** Coordinator SHALL require settlement status equal artifact verdict, `change_id` equal the active Change, and `candidate_sha == validator_head == current Candidate SHA`. PASS SHALL require `findings:[]`; risks, unverified, and open questions may be non-empty and SHALL be preserved. A valid FAIL SHALL contain at least one finding.
- **AC-M2-004-04 — Eligible repair and derived bytes:** A FAIL is eligible for the sole automatic-repair branch only when `auto_repair_attempt === 0` and every finding classification is `IMPLEMENTATION_IN_SCOPE`, every path is inside the frozen allowed scope, and all requirement/AC/evidence bindings are present; eligibility alone does not authorize continuation. The complete failed Validator AGENT_RUN and adjacent VALIDATION_RESULT records SHALL be read from canonical remote bytes before any repair transition. Coordinator SHALL derive the exact canonical `RepairTestDerivedEvidenceV1` only from those records plus current signed Change/scope, Candidate, cycle, and attempt identity. The repair-only binding SHALL carry the actual canonical bytes, byte length, padded-base64 round-trip, and derived hash while retaining the immutable signed Test base `input_sha256`. Base hash, derived bytes/hash, and Design's fixed framing uniquely determine the host-constructed effective input; no exposed effective-input hash or Coordinator base-byte reader exists. A guessed hash, substituted signed input, artifact-root publication, network read, or ordinary-role branch is forbidden.
- **AC-M2-004-05 — Causal cycle:** A repair Test PASS SHALL be produced only by the existing root-owned Host Loop after the Test Agent leader, pipes, and isolated process group close. The Agent SHALL emit only the closed finding-to-RED/control plan; the Host SHALL capture the complete final allowed Test bytes, materialize an independent read-only tree from the exact immutable Candidate Git objects plus those Test bytes, and execute each exact RED/control ID under Design 7.4's one fixed fully rendered `sandbox-exec` profile with the configured Node/Git executables, runtime uid/gid, closed cwd/env, separate scratch directories, shared deadline, and complete output capture. The distinct protected Host artifact SHALL bind exact plan/Test bytes, Candidate SHA/tree, execution-content hash, executable/runtime-root/profile identities, argv, PID, output bytes/hashes, and exit/TAP result; repair RESULT SHALL carry only its exact path/hash and closed summary for Coordinator/Ledger. Agent JSONL, declarations, TAP text alone, or post-close hashes SHALL never substitute. A-to-B or production modify/restore history is not retroactively detected: only a new rerun over final captured Test plus immutable Candidate can pass. Static route/capability mismatch before STARTED is `START_FAILED/ROUTE_UNAVAILABLE`; any content, process-group, isolation, schema, result, cleanup, or late mismatch after STARTED is `INTERRUPTED/RESULT_UNREADABLE`. Both request no Worker and admit no fallback.
- **AC-M2-004-06 — Budget and immediate stops:** Coordinator SHALL first remotely read back the exact attempt-zero Validator FAIL pair, prove eligibility and section 7.3 source/derived bytes, then persist/read back the sole budget transition `0 -> 1`. Only from that post-transition State version may it deterministically append/read back one repair REQUESTED, persist Pending/Action, and launch Test. Host proof PASS, repair RESULT summary/path/hash, complete AGENT_RUN and adjacent repair-bound Test receipt SHALL all be remotely read back before one Worker binding may carry that exact proof reference. Host SHALL revalidate proof and exact Test bytes before/after Worker, require no surviving process-group member, and bind its post-Worker WVEB snapshot; both Regression receipts and STAGE SHALL match that snapshot before Candidate. Pre-transition ineligible/mixed/unknown or wrong-Head/scope/evidence cases stop without consumption. Every failure/restart/late/substitution at or after budget transition remains consumed and permits no Worker continuation or proof retry. Runtime durable BLOCKED still requires normal failure/BLOCKED Ledger and BLOCKED State readbacks; unavailable Ledger retains the prior phase plus exact local pause. No new State field, event, Gateway, recovery boundary, budget, or public method is added.
- **AC-M2-004-07 — Second failure:** Any Validator FAIL after `auto_repair_attempt === 1` SHALL enter the existing `VALIDATOR_SECOND_FAIL / REVISION` disposition and SHALL perform no automatic continuation. Neither a new Agent instance, `run`, RESUME, nor RELEASE resets the budget. Only a signed same-scope REVISION starts a new authorization cycle as already specified.

### REQ-M2-005 — Closed Ledger Evidence, Stable Delivery, and Complete Handoff

K2 SHALL derive Candidate publication and Handoff only from exact current State, Git, Validator artifact, and remotely read-back Ledger bytes.

- **AC-M2-005-01 — Seven events with real context:** The only event classes remain the accepted seven. Every record SHALL use the exact record fields and detail union in Design with actual change, state version, subject, idempotency, receipt, and evidence context. Zero-version, all-zero subject, placeholder ID, truncated detail, or invented PASS/risk/path data SHALL be invalid.
- **AC-M2-005-02 — Receipt union:** `VALIDATION_RESULT.detail` SHALL be exactly the closed union of the legacy twelve-field role receipt and the twenty-four-field execution receipt. The twelve-field branch is limited to Test RED, Worker GREEN, and Validator review; the twenty-four-field branch is limited to the two WORKTREE Regressions and Candidate Final Validation. No field dropping, optional receipt bag, or compatibility projection is allowed.
- **AC-M2-005-03 — Canonical remote bytes and one shared object proof:** `ledger.readRemote` SHALL keep its exact public request and return the existing complete `LedgerRemoteReadReceiptV2`. The existing `production.mjs` SHALL export exactly one credential-free purpose-bound `createLedgerObjectReader({repositoryRoot,gitExecutable,runtime_uid,runtime_gid})`, returning one frozen `read` method whose exact request is `{remote_ref,expected_tip,tip,tip_tree,change_id}` and whose result is the existing `GatewayResultV1<LedgerRemoteReadReceiptV2>`. Construction and request objects are closed; roots/executable are trusted normalized absolute primitive paths, Git is the existing pinned executable, runtime IDs are nonnegative safe integers, and a non-root caller SHALL use its actual uid/gid.

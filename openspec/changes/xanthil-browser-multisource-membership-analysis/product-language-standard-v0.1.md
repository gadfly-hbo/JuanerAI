# JuanerAI 产品话术标准 v0.1

2026-10-09。供用户确认的草案；用户已认可语言方向，本稿尚未批准为全产品正式标准。

本稿由原 Change005 主 Agent 按用户直接要求整理。目标是统一 JuanerAI 的页面文案与 Agent 面向用户的表达；先在 Change005 应用，再由 PM 维护跨产品一致性。本稿不改动已冻结产品文件、UI 布局、业务含义、权限或状态机，不解除 pi-sdk 暂停，不声称实现或验收完成。

## 1. 面向谁，解决什么问题

用户以运营、经营和数据分析工作为目的，不需要学习产品内部工程概念。产品应像专业同事：理解问题，推动工作，清楚说明需要用户判断的地方。

默认表达围绕三个问题：现在在做什么；用户需要知道什么；下一步可以做什么。信息足够时，不必同时回答全部三个问题。不把每个状态都变成提醒，也不把后台严谨变成前台检查单。

## 2. 基本规则

1. **先说业务，再说系统。** “比较两个月的净销售额”，优于“执行当前分析框架”。
2. **用动作和结果说话。** “已保存”“需要补一份退款明细”，优于“草稿持久化成功”“当前不具备执行资格”。
3. **一句话承担一个目的。** 状态、解释和操作不要挤在一句中。相同提醒不在页头、卡片、抽屉重复。
4. **需要用户时，说明具体问题及影响。** 问“退款按原订单月份还是退款月份计入？这会改变每月净销售额”，不问“请确认期间口径”。已有资料能回答的，不再询问。
5. **不反复陈述否定。** 普通保存只显示“已保存”；是否开始分析由操作名称和当前状态表达。可能造成误解时，再就地提示“还没开始计算”。
6. **友好不等于模糊。** 不能隐藏未保存、失败、未知、未核验或外发范围，不能用“没问题”“放心使用”代替事实。
7. **不把措辞当作能力。** 不用“开始分析”包装仅保存，不用“已核验”包装模型自述，不用“已停止”包装仍在确认的请求。
8. **不责备用户。** 描述系统实际观察及可行下一步，不未经诊断要求用户解锁钥匙串、检查网络或重新配置。

## 3. 信息放在哪里

| 位置 | 表达重点 | 不应出现的负担 |
| --- | --- | --- |
| 中央对话／当前工作区 | 业务问题、重要发现、必要澄清、下一步 | 重复的内部状态解释、协议与工程术语 |
| 主按钮 | 点击后实际发生的动作 | “确认”“继续”等效果不清的词 |
| 短状态 | 已保存、正在分析、需要补充资料等 | 同时解释多个后台限制 |
| 口径／方案／证据抽屉 | 计算范围、资料来源、核验程度、版本影响 | 为简化而省略必要依据 |
| 使用说明／诊断详情 | 完整权限说明、技术原因和诊断标识 | 取代主路径上必须可见的风险或决策信息 |

主路径保留必要提醒；技术详情按需查看。关键权限、数字可信性和用户决策的信息不能藏进折叠说明。

## 4. 统一称呼与按钮

| 内部概念／原表达 | 默认面向用户的表达 | 使用条件 |
| --- | --- | --- |
| 需求框架／分析框架 | 分析思路、分析方案 | 讨论方向用“思路”；已有方法和范围用“方案” |
| 需求与分析框架 | 我们准备这样分析 | 展示当前分析安排 |
| 草稿已保存；保存没有启动分析 | 已保存 | 只有收到实际保存确认后才显示 |
| 保存框架，暂不分析 | 保存，稍后继续 | 只保存，不启动分析 |
| 读回已保存框架 | 查看已保存的方案 | 只读，不运行 |
| 当前框架尚待整体审阅 | 看看是否符合你的想法 | 请求用户核对业务理解，不替代权限授权 |
| 审阅当前框架 | 确认方案 | 保留原整体审阅动作；旁边必要时说明“确认后还不会开始分析” |
| 按此方案开始分析 | 开始分析 | 真实启动入口；既有权限和准入检查不变 |
| Binding／IR／Attempt／Harness | 不直接翻译到主路径 | 说实际字段、计算方法、范围或发生的事件；技术诊断保留精确名称 |
| 历史确认不适用于当前 revision | 方案已调整，需要再看一下 | 实质变化；不因纯措辞修改重复要求确认 |

“业务口径”“指标”“核验”等专业词可在适合的业务位置使用，并给出具体含义。不是禁止专业知识，而是避免让用户理解系统术语才能完成工作。

## 5. 常见场景文案

| 场景 | 推荐表达 | 事实要求 |
| --- | --- | --- |
| 保存中 | 正在保存… | 尚未确认，不能提前显示成功 |
| 保存失败 | 这次没保存成功，内容还在。可以再试一次。 | 只有输入确实保留时才能说“内容还在”；未知回执先核对再允许重试 |
| 保存结果未知 | 正在确认是否保存成功，请先不要重复提交。 | 不当作失败重新写入，不当作成功 |
| 缺必要资料 | 还缺退款明细。补上后，我才能计算净销售额。 | 明确缺什么、影响什么；可以保存现有工作 |
| 业务歧义 | 退款计入原订单月份，还是退款发生的月份？这会影响月度比较。 | 仅询问影响计算或重要判断、资料不能解决的歧义 |
| 正在推进 | 正在核对订单和退款的对应关系。 | 来自真实执行状态，不播放虚构步骤 |
| 部分失败 | 月度结果已保存；地区比较没完成，可以重试这一部分。 | 对应真实有效部分成果；不能笼统写“分析失败”或假称全部成功 |
| 模型解读 | 从现有数据看，… | 不把推测写成原因；区分可见事实与解释 |
| 无法判断原因 | 现有资料只有退款金额，还不能判断原因。需要补充退款原因或相关记录。 | 不编造原因，也不把缺证据当“没有原因” |
| 用户停止中 | 正在停止，已有结果会保留。 | 停止尚未确认；只对确实保存的成果承诺保留 |
| 已停止 | 已停止。可以稍后继续。 | 停止已确认；“继续”必须是显式且适用的恢复动作 |
| 请求结果未知 | 上次请求的结果还没确认，核对后才能继续。 | 不显示为成功，不重置消耗或自动重复执行 |

实例是表达模板，不是固定业务回答；字段、部分成果、原因与可行下一步必须由实际状态提供。

## 6. 数字可信性与权限不能简化掉

- 已有独立核验：在关键数字附近显示“已核验”，展开后说明核验方法、来源、范围和限制。只通过算术一致性时，详情准确说明，不升级为业务正确或因果成立。
- 仅部分覆盖：显示“部分核验”，说明哪些数字经过核验、哪些没有。
- 实际计算但未独立核验：显示“已计算，尚未独立核验”，保留可检查来源；不显示绿色通过。
- 存在不一致：显示“发现计算不一致”，指出受影响数字；不将其作为可信结论发布。
- 预演可能答案：在预演区域标一次“可能的解释，还需要资料验证”；它是候选假设，不能显示为已经发生的经营事实或报告结果。
- 模型外发、资料权限、原件修改、现实行动：需要用户决定时，说明具体发送／修改什么、接收方或作用对象以及实际效果。不得用“继续”“确认方案”代替必要授权。
- 用户单位与币种：保持准确，不为话术顺畅省略单位或把未经确认的单位当事实。

与既有 R3、需求沙盘及停止／UNKNOWN 合同冲突时，保留其真实边界，并寻找更易懂的表达；不通过删除提醒消除冲突。

## 7. 版本变化

先说业务变化，再说成果影响。例如：

> 这次只看 Coffee，上一版包含所有商品。两个月的净销售额和增长率需要重新计算；上一版结果仍可查看。

版本号放在详情或比较处，不让“revision／失效／重算资格”等词主导主路径。用户仅查看旧版本不触发重算；旧结果不能冒称当前结果。没有实际完成重算时，不说“已更新结果”。

## 8. Agent 回复也遵守同一标准

理解、推进和回答围绕用户的业务。非必要不逐步宣讲检查机制，不在每次回复重复资料权限或核验免责声明。说明真实缺口时给出具体补充建议；能依据已有资料推进的，不制造审批或问卷。

模型输出的友好程度不替代结果检查。需要改写时，保持数字、单位、来源、限制、权限与版本事实，不引入新结论。此标准不直接授权改模型提示、Runtime 或 SDK；相关实现仍遵守当前暂停及工程边界。

## 9. 如何落实与维护

- **PM：**维护产品称呼、语气、跨页面一致性，以及会影响业务含义或用户判断的话术决定。
- **主工程 Agent：**盘点真实文案，按已批准标准落实固定文案；核对真实状态和按钮效果，保留必要负例与证据。
- **用户：**确认表达是否易懂、符合业务习惯，决定涉及产品含义或边界的取舍。
- **独立 Validator：**在完整候选审阅中核对实际效果、成功／失败／未知／权限含义是否准确；不另设日常文案审批流程。

先复用本稿，不新增语言运行层、状态系统或强制文案工具。正式采用后，在既有 UI Contract／设计中引用唯一标准；冻结输入及历史证据保持原样。普通语句调整在包内推进；改变按钮效果、核验承诺或权限含义时提出具体差异。

验收检查：非技术用户能看懂正在做什么及可行下一步；同一信息没有无意义重复；实际保存前没有成功文字；缺资料说明具体缺口；模型解释与独立核验可区分；权限与停止未知不被隐藏；新旧成果归属准确；原布局和功能不丢失。

本次仅交付标准草案与修改示例。全产品文案盘点、替换与实际页面回归为后续采用工作；不将草案落盘报告为已完成全产品整改。
